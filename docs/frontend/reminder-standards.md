# Reminder 待办提醒规范

待办表单与事项类型表单的弹窗底部统一使用全局 `tf-dialog-actions`。PC 端“取消、保存”按内容自适应并靠右，手机端居中等分保持一行；页面内不得重复维护按钮宽度规则。颜色选择器是独立浮层，其清空/确定按钮继续使用颜色面板专用紧凑布局。

## 功能边界

Reminder 用于创建一次性或周期性待办，支持指定员工或创建时的全体在职员工。事项类型只负责分类和默认提前天数；具体标题和内容始终允许自由输入。

支持的周期：

- `once`：只执行一次
- `daily`：每隔 N 天
- `weekly`：每隔 N 周，可选择多个星期
- `monthly`：每隔 N 月的指定日期
- `yearly`：以首次执行日期为基准，每隔 N 年执行

每月和每年都不再重复选择日期规则。用户只需选择首次执行时间和周期间隔：每月自动沿用首次执行时间中的“日”和时分，每年自动沿用首次执行时间中的“月、日”和时分。目标月份不存在该日期时自动使用当月最后一天，例如 1 月 31 日的月度待办在 2 月按最后一天执行，2 月 29 日的年度待办在非闰年按 2 月最后一天执行。Reminder 页面执行时间输入和展示使用 `YYYY-MM-DD HH:mm`，数据库继续使用 `DATETIME` 兼容历史数据；每天和每周待办默认从创建当天的当前时间开始计算。每次周期执行都生成独立员工记录，上一周期的完成或忽略不会影响下一周期。

表单先选择重复方式。“提醒时间”只在不重复、每月和每年时显示：不重复用于指定唯一提醒日期，每月用于提取每月几号，每年用于提取月和日。每天和每周不显示日期字段，默认从创建当天开始计算；每周以选择的星期为固定执行规则。

指定员工下拉只展示在职员工（`users.status = 1`）；后端接口和前端选项均进行状态过滤，保存时后端再次校验接收人状态。

待办主列表操作列使用“图标 + 文字”的查看、编辑和删除按钮，列宽根据当前权限下实际显示的按钮数量动态计算，按钮不得省略文字或超出单元格。

“事项”标题使用全局 `el-button.table-inline-action.table-action--view`，浅青蓝背景、深青蓝文字及悬停/聚焦效果复用公共查看配色，保留点击查看详情；PC 28px、手机 32px 的高度和单元格留白由公共表格入口控制，数据行保持 PC 48px、手机 40px。标题列通过 `getTextColumnMinWidth` 按当前列表计算最小宽度，长标题单行完整展示，窄屏只在表格内部横向滚动；不得使用多行内容按钮或页面私有尺寸。

## 编辑与提醒时间

提醒开始时间为“执行时间减去提前提醒天数”，并非始终到执行时刻才弹出。例如执行时间为当天 21:00、提前提醒为 7 天时，员工当天 21:00 前收到提醒符合提前提醒设置；需要到 21:00 才提醒时，应设为 0 天。

编辑始终更新原任务 ID，不得无条件删除并重建执行记录。一次性任务改期，以及同一周期调整执行时间（例如 00:00 改为 21:00），沿用原记录和已完成、忽略、稍后提醒状态，保留操作时间及提示节流；只改标题、内容、类型或提前提醒天数也不能重置完成状态。周期匹配以每天/每周的执行日期、每月的月份、每年的年份区分，真正进入下一周期才生成独立记录。新的提醒时间同步到已有记录；稍后提醒超出新的“执行前 3 小时”上限时收紧到该上限。不再属于当前规则或接收范围的未完成记录应移除，已完成和忽略记录保留历史。“全体员工”任务编辑时继续沿用已保存的人员快照，只有从指定员工切换为全体员工时才重新取在职员工。

同一员工、同一周期只维护一条有效执行记录：“待处理 → 稍后提醒 → 已完成”都更新原记录 ID，不为每次操作新增状态行。员工在提醒开始后、执行时间前提前完成，也直接进入本周期完成终态；到执行时刻、再次登录或轮询补齐记录时不能重新生成待处理行。历史改期已产生“同周期完成记录 + 多余未完成记录”的，保留原完成记录 ID 和操作时间，移除多余未完成记录并同步原记录的执行及提醒时间；真实数据修复先只读预览，确认授权后在事务内执行。

状态写入必须在数据库条件中排除已完成记录，防止多窗口并发的旧“稍后提醒、已读、忽略”请求覆盖完成状态及完成时间；重复提交完成保持幂等。

全局提醒每次轮询重新校验已排队记录，更新改期后的内容，撤下尚未到新提醒时间、已处理或已删除的旧记录；不以缓存响应恢复旧弹窗。`GET /reminders/my/pending` 支持可选的逗号分隔参数 `queued_occurrence_ids`（最多采用 100 个有效 ID），仅用于校验当前用户队列：仍须满足本人、任务启用、记录未完成、已进入提醒期及稍后提醒到期等条件，只豁免这些队列记录的重复提示节流，且不重写其上次提示时间。

回归入口：`node --test backend/test/reminder-scheduling.check.js backend/test/reminder-controller.check.js`、`npm --prefix frontend run test:unit -- tests/reminder-host.spec.ts`。

## 精简数据模型

数据库使用四张表：

- `reminder_types`：类型名称、默认提前天数、颜色、图标和启用状态。
- `reminders`：事项模板、自由文本、接收人 JSON 快照、周期规则 JSON、开始时间、提前天数和状态。
- `reminder_records`：每位员工每次执行的提醒时间、执行时间、状态、操作时间、稍后提醒时间和上次提示时间。
- `reminder_completion_views`：管理人员对完成反馈的确认记录，以执行记录和管理人员联合去重；确认反馈不改变员工已完成状态。

周期规则和接收人快照使用 JSON，避免为每个周期字段和目标范围增加重复列。执行记录使用 `(reminder_id, user_id, scheduled_at)` 唯一键，防止轮询或重复登录生成重复待办。

## 员工状态

`reminder_records.status` 只能是：

- `pending`：待处理
- `read`：已读
- `snoozed`：稍后提醒
- `ignored`：忽略本次
- `completed`：已完成

完成或忽略时写入 `action_at`。后台详情按员工和执行日期展示状态及操作时间。

待办弹窗只提供“稍后提醒”和“已完成”。稍后提醒必须早于本轮执行时间至少 3 小时，且服务端会保存下次提示时间，因此退出后在到期前不会重复弹出。提醒进入执行前最后 24 小时后，未完成记录每小时最多提示一次；超过执行时间仍未完成时继续按小时提示，直到员工完成。完成是当前周期的终态，完成后不得改回其他状态且不再弹出；下一周期使用独立记录，不受上一周期完成状态影响。详情在已完成历史之前展示未完成记录，并为每位员工展示最近一轮尚未进入提醒期的真实记录；指定 2 人即对应 2 条，不为状态操作额外建行。未操作且未到执行时间的“操作日期”显示“未到执行时间”，到期仍未操作显示“尚未操作”；已有操作显示真实北京时间到分钟，执行和提醒时间也展示到分钟。

## 权限

权限模块为 `reminders_reminderview`，标准权限为：

- `reminders:view`
- `reminders:create`
- `reminders:edit`
- `reminders:delete`
- `reminders:manage`

`manage` 用于事项类型管理和全量维护。接收人只能操作分配给自己的记录，不需要额外的完成权限。

待办列表和详情必须执行后端数据隔离。普通 `view` 用户只能看到分配给自己的待办，列表统计、接收人和执行记录都只返回本人数据；拥有 `reminders:manage` 的用户才能查看全部员工记录。前端隐藏不能代替后端过滤，直接请求其他员工的待办详情应按不存在处理。

事项类型管理表格使用内容驱动的自适应列宽：内容较少时铺满弹窗，类型名称较长时完整显示，空间不足时只使用 Element Plus 表格内部横向滚动。操作列提供编辑和删除；未被待办使用的类型可以删除，已被待办使用的类型只能停用，避免历史待办失去类型关联。

待办执行记录弹窗表格遵循全局弹窗表格规则：执行日期、提醒时间、员工、状态、操作日期五列按当前记录计算紧凑最小宽度，不继承主列表固定最小宽度；记录较少时自动铺满弹窗，手机端空间不足时由同一个 Element Plus 表格容器横向滑动，表头与内容同步且字段不省略。

新增和编辑事项类型展示类型名称、默认提前天数、识别颜色和排序。颜色选择器右侧实时显示类型标签预览，点击或拖动颜色面板时立即更新文字、边框和背景，不需要先确认；图标保留为内部兼容字段，页面不提供图标 class 输入。

## 手机端模态框操作栏

新增/编辑待办和新增/编辑事项类型的底部操作统一使用 `dialog-footer` 容器。取消和保存必须在同一行横向展示，取消在左、保存/确认在右；手机端按钮居中等分并受最大宽度限制，不得换行、纵向堆叠或被裁切。业务页面不得为手机端单独写 `flex-direction: column` 或固定的 `width: 100%` 按钮布局。颜色选择器使用 `teleported` 挂载到 `body`，宽度不得超出视口。由于项目手机端公共遮罩层使用 `z-index: 9999`，嵌套模态框内的颜色选择弹层必须使用高于 `9999` 的专属层级，确保面板显示在遮罩和编辑模态框上方。

## 全局提醒

后台主布局加载 `ReminderHost.vue`。登录完成、窗口获得焦点和每 60 秒会查询 `/reminders/my/pending`。服务端按普通提醒每 6 小时、执行前最后 24 小时每 1 小时节流，队列内同一执行记录不重复排队，普通关闭后仍按服务端节流提示；员工选择稍后提醒或完成后，状态写回后端。第一版不发送短信、邮件或微信通知。


## 最后 3 小时与首页公告

前后端强制窗口统一读取 `backend/src/config/reminder-policy.json` 的 `mandatory_hours`，当前为 3 小时。该文件随完整 `backend/src/config/` 发布，后端运行不依赖项目根目录 `config/`；前端在构建时引用同一份 JSON，不保留第二份策略。提醒开始后，执行时间减去 3 小时起（含边界，逾期继续）强制显示本人未完成任务，优先按执行时间处理；普通通知开关、普通提示节流、已读、忽略或历史稍后时间不能绕过。服务端在状态写入时校验窗口，除完成外不得操作，并在 SQL 条件再次校验执行时间，防止并发改期绕过。完成终态和幂等要求继续适用。

`GET /reminders/my/active` 使用统一认证、本人身份和执行状态字段权限，响应沿用提醒字段脱敏；`is_mandatory` 是执行状态权限下的布尔控制信息，隐藏执行时间时仍能强制提醒，不返回被隐藏的具体时间。只返回启用任务中已经到提醒开始时间、尚未完成的本人执行记录；包含稍后提醒中的记录，不更新提示节流，也不让下一周期遮蔽逾期任务。`frontend/src/stores/reminders.ts` 保存此清单、响应式时钟与写入代次，全局 Host 登录、聚焦、恢复可见和每分钟刷新，时钟每秒检查窗口。公告和强制弹窗共享此清单；完成后立即移除，旧请求不能恢复已完成记录。

强制窗口前允许关闭普通弹窗，关闭不修改执行记录状态；仍可选择稍后提醒或完成。强制窗口内公共 `MobileDialog` 禁止关闭按钮、遮罩、Escape 和关闭回调，路由导航与主动退出登录也受阻（退出限制使用现有认证 Pinia 的临时 `exitLock` 状态，不持久化；任务完成、权限撤销或 Host 卸载时解除），所有强制任务完成后恢复。认证过期、密码修改等安全退出不阻止；浏览器关闭/刷新仅通过 `beforeunload` 请求原生离开提示，不能保证禁止关闭浏览器。

首页 `/dashboard` 复用现有公告区域，显示“员工姓名，您的待办没有完成哦！本次需要完成的内容：……。请及时安排好时间完成任务！感谢支持！”。姓名取本人认证资料，任务标题、内容及执行时间遵循 reminders 字段权限。任务未到提醒期不展示，稍后提醒期间仍展示，完成立即消失。个人提醒不写入公共公告表，不向其他员工广播；关闭普通通知也不隐藏此业务公告。

提醒领域共享类型唯一入口为 `frontend/src/types/reminder.ts`，由全局 `types/index.ts` 导出，页面、全局 Host 与 Pinia 不再各自维护响应类型。
