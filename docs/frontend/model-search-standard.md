# 型号检索统一规范

## 目的

型号属于品牌下的从属选项。业务页面应先确定品牌，再加载该品牌全部有效型号供本地筛选；不得只取排序靠前的固定数量，否则后续型号无法被搜索到。不得一次加载全库所有品牌的型号。

## 统一流程

1. 先选择品牌，型号请求必须携带 `brand_id`。
2. 对品牌下的完整有效型号集合进行筛选；若页面采用远程搜索，则关键词通过 `name` 参数发送，后端不得再以固定条数截断匹配结果。
3. 异步搜索使用防抖或请求序列号丢弃旧响应，避免快速输入时旧结果覆盖新结果。
4. 编辑已有设备时携带 `include_id`，确保当前型号即使停用也能回显；该记录仅用于编辑回显，不进入普通新增筛选。
5. 后端按 `sort_order`、型号名称、ID 稳定排序，并返回所选品牌下全部有效型号；该参考选项接口不分页，不得增加固定 `LIMIT`。
6. 未选择品牌时不请求型号列表。每次品牌切换应清空旧型号值和旧选项，防止跨品牌误选。

## 公共接口

后台业务页面使用：

```text
GET /api/query/models?brand_id=品牌ID&name=关键词&include_id=当前型号ID
```

该接口使用综合查询查看权限，返回标准型号字段：`id`、`name`、`brand_id`、`brand_name`、`sort_order`。普通筛选默认取得所选品牌下的全部启用型号；传入 `name` 时返回全部匹配结果，不应用 50 条等固定上限。若未来数据量需要响应保护，必须新增可继续翻页的协议，不能静默丢弃后续型号。

前端公共入口为 `frontend/src/services/reference-options.ts` 中的 `getCachedModelsByBrand`。入库、综合查询筛选和综合查询编辑应复用该入口或同等的品牌型号请求。只加载当前品牌范围；接口返回必须完整，不能通过截断选项集来限制数据量。

## 例外

型号管理页面自身仍可使用分页列表，用于管理和排序全部型号。这个管理列表与业务表单的远程下拉不是同一个加载场景。
