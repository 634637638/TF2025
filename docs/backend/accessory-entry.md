## 采购入库防重与异常恢复

`POST /accessories/stock-in` 必须提交32位小写十六进制 `request_key`，模板新增/编辑不携带该字段。`AccessoryController`只在采购入口转发此事务元数据，实际入库员仍取认证身份。数量、进价和分配数量在转换前复用公共整数/金额校验；门店、供应商及商品关联编号拒绝数组和布尔值。SN仍按实际有效录入件数计量。

入库弹窗提供“入库时间”，默认当前秒级北京时间，可选择实际到货时间；单色及多颜色采购均使用可选 `inventory_time`，格式为完整 `YYYY-MM-DD HH:mm:ss`。服务端公共时间校验拒绝不存在的日期、时分秒溢出及尾随内容；同组各颜色必须相同。显式时间纳入防重摘要并用于采购业务时间、SN及库存流水，重试保持原值；旧客户端省略时由服务端生成当前北京时间，同组只生成一次，原省略字段的摘要保持兼容。字段沿用 `time_info.inventory_time` 权限，隐藏时不展示或提交。原入库更正只读展示原时间，本次不开放修改历史批次时间；采购记录的系统创建时间仍独立保留。

原 `accessory_stock_in` 表追加可空 `request_key CHAR(32)`、`request_hash CHAR(64)`，使用 `ascii_bin` 与 `uq_accessory_stock_in_request(request_key)` 唯一索引；历史采购保持NULL，不补造请求。摘要绑定实际操作者、商品及模板输入、供应商、实际品牌、店铺分配、分币成本、实际数量、用途、SN和备注，省略与显式NULL保持区别。原采购、库存批次、SN和事件沿用同连接事务。重复请求返回原采购；并发唯一冲突先回滚竞争事务，再读取已提交采购核对，不能再次生成库存或整批应付。同键更改内容或更换操作者返回409 `STOCK_IN_REQUEST_CONFLICT`，不透出原请求内容；重新核验全部原分配店的当前授权。缺字段、错误字段结构、缺完整唯一索引或非InnoDB返回409 `STOCK_IN_NOT_READY`，运行时不执行DDL或降级。

成功回执统一为 `stock_in_id/batch_no/accessory_id/quantity/total_amount/inventory_time/replayed`，重放除 `replayed=true` 外保留原事实，不重新读取后来变化的模板或库存快照。服务端核对原数量、单价乘数量、供应商及分配凭据后返回；不返回请求键或摘要。原采购ID随批次号字段权限遮蔽，数量、总额和时间沿用原字段权限，NULL不当成0。

多颜色入库复用同一路径，提交 `{ request_key, entries: [单颜色入库资料] }`，每项不再携带请求键；响应为 `{ batches: [原采购回执], replayed }`。服务端按颜色采购根ID稳定排序，首批使用整组请求键，其他批次键由整组键和颜色采购根ID确定；每批摘要同时绑定完整整组内容，不能增删颜色、改数量或拆成单批重放。全部颜色在同一连接和事务中生成各自采购、应付、快照、库存及SN流水；任何一色失败整体回滚，不存在前端循环请求造成的部分成功。并发竞争回滚后只能核对完整原组；提交后断连使用原组、原键重试，不重读后来模板替换原事实。旧单批请求及回执保持兼容，复用既有防重字段，不新增表或迁移。

前端 `stores/accessory-stock-in.ts` 通过统一存储服务，在当前浏览器标签页会话中按认证入库员保留一笔未确认采购。首次发请求前必须完成持久化并回读；失败不发送。网络/超时/服务端故障、结构未就绪或缺完整回执时，关闭弹窗、组件重建或刷新页面仍保留原载荷与标识，显示“重试原入库”，确认前暂不另建采购。恢复时验证唯一DTO及当前字段权限，隐藏字段不重新发送；请求期间禁止连点和关闭，并复用公共SectionLoading显示“正在提交并核对入库结果”，此时不显示“上次入库结果尚未确认”。请求结束后仍未收到完整回执或重开仍有未确认凭据时，才显示重试警告；提示变化不清理原凭据，也不另建入库请求。模板编辑保持独立。仅服务端明确400业务拒绝且确认未提交的错误释放凭据供修正；成功必须收到完整原回执并成功清理凭据，再通知父页刷新。会话存储不能承诺清理浏览器数据、关闭标签页后的恢复；此时须先通过原采购记录核对结果，不能凭未知结果重复创建。

`npm --prefix backend run migrate:accessory-stock-in-requests` 默认只读预览。应用需暂停入库、保留完整数据库备份并传 `-- --apply --backup-file=<受控备份路径>`；脚本以0600、拒绝覆盖的文件保存原表结构及完整行，迁移前后核对全部原字段摘要，已有冲突结构拒绝覆盖。`--rollback` 仅在新增字段均无值时可用，已有任一请求键或摘要即拒绝删除凭据。部署前完成迁移核验并更新前后端；2026-11-14已获授权执行此结构迁移并回读，真实采购未验收。

正式回归为 `backend/test/accessory-stock-in-requests.check.js`、原入库/SN/批次事务测试，以及 `frontend/tests/accessory-stock-in-state.spec.ts`、`accessory-entry.spec.ts`。替身事务覆盖并发唯一竞争、提交后断连、提交前失败、SN重放、身份/字段边界及迁移保护；不替代真实MySQL并发或真实采购验收。

## 采购入库原资料留存

新采购在原入库事务、根模板锁内，对最终实际商品及本次供应商、原入库店执行当前共享锁定读，避免等待模板锁之前建立的可重复读旧快照。服务端只保存版本1白名单：商品/供应商/门店ID，以及名称、商品类型、实际品牌、配件型号、颜色、单位、供应商名称及原店名称，写入原 `accessory_stock_in.product_snapshot JSON NULL`；不新增业务表，不接受客户端快照。原数量、单价、整批金额、时间和认证入库员仍来自原采购列。任一步骤失败同事务回滚；幂等重试只返回原回执，不用后来资料覆盖原快照。

采购货款列表、退供核对及原价试算、入库历史先投影原资料，再由原公共字段服务脱敏；不向客户端返回内部JSON。新单返回 `has_snapshot=true`，原字段为NULL也保持原值；历史NULL快照返回false，保留当前关联资料并在采购页明确标记“当前档案（旧单无快照）”，不回填或声称历史原名。非空快照损坏、版本未知、缺字段或商品/供应商/门店身份不符返回409 `PURCHASE_SNAPSHOT_CONFLICT`，不静默降级。商品名、品牌名、供应商名及原入库店名检索使用同一快照优先规则与绑定参数；货款页四项条件均支持可输入下拉选择和模糊搜索，仍受字段权限控制。`GET /supplier-payments/accessory-purchases/options` 为货款筛选返回选项：供应商和品牌合并启用且业务范围含配件的主档与授权范围内历史采购快照，商品取历史采购商品，店铺返回当前账号有权访问的全部启用门店并合并授权历史采购快照；隐藏字段不会返回对应选项。

当前批次库存、SN详情/流水和商品销售来源的采购供应商名称共用快照优先投影；当前库存门店仍表示实物现位置，不改成原入库门店。`GET /accessories/stock-in/records` 使用认证用户的原入库店及全部历史分配店授权，数量与行查询共用整单范围，后来划拨不授予原采购查看权；越店及非法分页在仓储查询前拒绝。

受控命令 `npm --prefix backend run migrate:accessory-purchase-snapshots` 默认只读预览。实际执行先暂停采购写入并保留完整备份，再传 `-- --apply --backup-file=<受控新备份路径>`；脚本独占创建0600原结构/完整行备份，仅添加可空JSON列，并核对全部原字段摘要不变。非InnoDB或冲突字段拒绝迁移；不回填旧单。`--rollback --apply --backup-file=<新回退备份路径>` 仅允许所有快照为NULL，有任何原资料即拒绝删列。部署依赖本字段的版本前必须先完成此迁移及前述防重迁移；运行时缺任一结构拒绝新入库，不自动DDL。**2026-11-14已授权迁移并回读；结构就绪不代表真实采购已验收。**

正式回归：`backend/test/accessory-purchase-product-snapshot.check.js`、`accessory-stock-in-requests.check.js`、`accessory-purchase-return-context.check.js`，以及采购付款/核对前端专项。覆盖原资料、同连接锁边界、客户端伪造无效、坏快照拒绝、字段脱敏、整单门店范围及迁移/回退保护；事务替身不替代MySQL多连接或真实采购验收。

## 商品库存原入库更正

`/accessories` 的“库存查询”改为“商品库存”，顶部新增模板按钮改为“商品模版”。商品库存行保留“编辑”作为原入库数量/成本更正，并新增“编辑档案”处理配件品牌、名称、类型、适配型号、配件型号、颜色、单位及零售价等商品资料。档案编辑在移动/桌面表单中并排显示修改前后资料；历史采购快照和共同销售/赠送商品快照同步更新，未留快照的旧销售继续从当前商品档案读取。采购/销售数量、成本、成交价、付款、退款、退货、库存流水、SN和时间均保持原值。商品资料使用 `accessories:edit` 与原字段拒写/脱敏规则，并通过公共业务日志记录操作人及修改前后商品资料（沿用运行日志保留周期，不是永久数据库审计）。更换品牌遇到同模板已有目标品牌库存商品时拒绝合并，须先由用户核对重复档案，避免关联库存和历史单据被合并。

单颜色模板的可编辑档案字段双向共享，包含名称、条码、类型、适配型号、配件型号、颜色、单位、默认零售价、图片、说明、备注、启用状态、预警值及SN默认开关。多颜色模板按下节区分公共字段与各颜色的独立条码。模板或库存“编辑档案”保存后，同模板全部品牌商品统一读取根模板资料；停用或重新启用同样联动，旧子商品副本不覆盖模板空值或启用状态。实际品牌、采购来源与库存独立；SN开关只调整模板默认值，不转换既有库存。档案修改、快照同步和商品主档写入处于同一数据库事务；采购原更新时间显式保留。独立商品主档编辑不修改采购成本、供应商、批次数量或单据金额；采购批次账务更正仍使用下方“商品库存原入库更正”。

档案入口为 `PUT /accessories/:id`，`:id` 使用库存行实际商品ID；沿用原认证、`accessories:edit` 和字段拒写中间件。修改前后对照同样过滤隐藏字段。此前一轮同步SQL仅在真实云端执行过只读 `EXPLAIN`；本轮全部字段联动以隔离行为测试核验，浏览器使用内存接口验证桌面/平板/手机入口和保存，不代表已经提交真实档案更正。

接口均使用统一认证、`accessories` 权限及原入库店/全部分配店范围：

| 接口 | 用途及要求 |
| --- | --- |
| `GET /accessories/:id/stock-in-options?page=1&page_size=20` | 精确实际商品ID的有效原采购分页，要求view及edit |
| `GET /accessories/stock-in/:id/edit` | 同连接只读RR核验并回填原数量、成本、供应商、门店、用途和SN，要求view及edit |
| `POST /accessories/stock-in/:id/corrections` | edit及字段拒写守卫；保存原批次更正 |

商品库存列表、商品详情及条码详情的展示进价，统一读取当前授权原采购范围内最近一笔 `completed` 入库的 `purchase_cost`，按原入库时间、批次ID倒序确定；已作废的更正原单不参与，0元是有效价格。没有符合条件的采购时沿用历史主档参考值，不据此补造批次成本。更正保存后主列表重读该投影，避免主档原值0遮盖已保存的新批次进价；修改较早批次不会覆盖更新入库的展示价格。商品主档、其他品牌和其他采购成本不回填，销售成本仍由实际出库批次计算。前端提交前重新读取字段权限，同账号、动作及字段可见性值未变时保留更正凭据；实际撤权仍清理并阻止提交。

提交仅接受 `request_key/accessory_id/brand_id/product_model/supplier_id/store_id/total_quantity/purchase_cost/usage_type/serial_tracking/serial_numbers/remarks`，复用原采购整数、分币金额、启用引用及SN校验。数量上限999999，SN最多1000件，归属本次所选同一门店；隐藏可选字段不发送默认空值，备注可明确清空。原入库员和入库时间不被客户端改写，更正人及时间另存审计。

当前只开放**原资料快照和原批次正向入库流水完整，且无任何后续业务、付款/撤销付款历史**的整批更正。出现销售、赠送、划拨、返库等即拒绝，净余量后来恢复也不抹除历史；缺快照/流水返回409 `STOCK_CORRECTION_UNTRACKED`，原单已更正/作废为 `STOCK_CORRECTION_STALE`，后续库存业务为 `STOCK_CORRECTION_USED`，付款为 `STOCK_CORRECTION_PAID`，账差沿用 `INVENTORY_LEDGER_CONFLICT`。旧多店分配或实际分配店不是原入库店时返回 `STOCK_CORRECTION_DISTRIBUTION`，避免单店表单保存时静默合并或移库。旧单不能凭当前主档或商品汇总补造原批次来源；历史资料调整仍归T22.10。

正确SN保留逐件ID；错误SN软作废为 `voided`、保留事件，并随替代批次追溯，后续更正可恢复该批误删SN；不能挪用其他批次SN。当前批次型号读取采购快照，不能更正了型号却仍展示主档默认型号。HTTP仅返回业务投影及统一入库回执，不透传审计JSON/请求摘要。前端关闭/换批/撤权取消旧读取；结果不确定时冻结原载荷，“重试原更正”使用同键核对，原批次唯一更正约束阻止另开表单重复调整。此恢复仅限当前弹窗；关闭后须通过原批次状态核对，不能声称跨刷新持久恢复。

## 原采购单退供核对

商品采购页的“退供核对”调用 `GET /supplier-payments/accessory-purchases/:id/return-context?page=1&page_size=20`，可选 `store_id` 限定当前库存门店。此入口只读，不提交退供、冲减应付、登记退款或生成退供凭据；采购退货资金规则及实施进度统一登记T22。

原采购的在库SN通过同一响应 `serials: { data, pagination }` 返回，与原采购、付款及批次余额共用同一只读快照。`serial_page` 独立控制SN页码（默认1，上限1000000），每页大小共用 `page_size`（1–100）；`serial_search` 可选，最多100字符，拒绝对象、数组、控制字符等非法原值，按去首尾空格后的字面子串匹配，`%/_` 不作通配符。搜索仅影响SN列表及其总数，不改变整批剩余数量。查询精确限定原采购的实际商品ID、`stock_in_id`、`status=in_stock` 和当前授权店铺，不混入同模板其他品牌/批次、已售或已赠出的SN；明细仅含 `id/serial_number/store_id/store_name`，保留前导零并按逐件ID稳定分页。页面提供SN检索、独立分页及手机双击详情，末页因出库消失时回有效页重读。

SN明细额外受配件模块 `basic_info.serial_number` 控制。字段隐藏时不查询逐件资料，`serials=null`；此时传入 `serial_page/serial_search` 返回403，避免用搜索推断SN。历史原入库缺完整流水时同样 `serials=null`，不把未知来源当作零件。前端关闭、换单、撤权清空SN明细/检索并取消在途请求；返回缺字段、重复SN或不完整分页均显示核对失败，不当成空记录。

原采购整单沿用货款页原入库店及全部历史分配店的授权条件；当前批次另按账号授权门店过滤，不能因可看原整单而看到已划至其他未授权店的库存。服务层使用与付款历史共用的本业务只读事务入口，单连接 `REPEATABLE READ, READ ONLY` 快照同时读取原采购、完整付款追加链、原入库流水及当前批次；结束回滚只读事务，配置/启动/回滚失败销毁连接并由公共helper释放，不锁库存，不追加期初或运行迁移。页大小1–100，未知参数、数组/布尔ID或越权店铺在取得连接前拒绝。

响应 `purchase` 保留原供应商、采购数量、采购单价、原整批金额、原店及入库时间/入库员；名称、品牌、型号及来源标记按[采购原资料契约](#采购入库原资料留存)投影，新单为入库时资料，旧单明确当前档案。`paid_amount/unpaid_amount/payment_status/latest_event_id` 来自按游标逐段核验的完整付款链，不能只信最新一行；打款/撤销须交替、原采购/供应商/整额一致，撤销准确引用上一有效打款。零采购可核对，无有效打款；原数量乘单价不符、重复打款、孤立撤销或错原引用返回409。

付款链的方式及时间同样逐条核验：方式属于公共结算选项，时间为有效的完整秒级北京时间，撤销与其原登记的方式/时间完全一致；坏记录返回`PURCHASE_PAYMENT_CONFLICT`，不进入库存候选和试算分配，不补造原时间。新登记输入及后续重新登记沿用[商品采购货款契约](../payments/SUPPLIER_PAYMENT_BATCH_STANDARD.md#数据与一致性)，不改变当前只读退供边界。

`ledger_status=verified` 表示原入库流水数量/成本以及授权当前门店的库存/SN账核对通过；`current_quantity` 仅为授权范围内该采购批次剩余量，`data` 按当前门店、原成本、用途及普通/SN方式分组分页，`pagination.total` 是组数。只查原实际商品与指定入库ID，其他品牌、批次或无来源库存不混入。SN另按原入库/门店/成本双向核对，防止总SN数相同却串批。原采购整额不随这些余额变化。

历史缺完整原入库流水时返回 `ledger_status=untracked`、`current_quantity=null` 及空列表，页面显示无法确认可退数量；这不等于零库存。库存账或原入库不一致返回409 `INVENTORY_LEDGER_CONFLICT`，付款账错误返回 `PURCHASE_PAYMENT_CONFLICT`，结构缺失返回 `PURCHASE_RETURN_NOT_READY`，不使用当前主档供应商或成本填补。

接口同时要求 `supplier-payments:view` 和 `accessories:view`，复用两个模块严格 `FieldAccessService`。原采购数量、供应商、店铺、成本/总额、付款状态及当前库存门店/数量为核对必需，任一隐藏均403且不读业务数据；其余采购资料、库存成本/用途/SN方式分别遮蔽，权限故障拒绝读取。原采购内部批次ID及幂等摘要不放入库存行。PC操作列与手机双击详情底部使用相同入口；弹窗复用公共描述、表格、分页、Loading、手机记录详情及最新请求，关闭、切单和撤权清理已读数据并取消旧请求。

### 原采购价退供试算

`POST /supplier-payments/accessory-purchases/:id/return/quote` 仅接受请求体 `{ batches: [{ row_key, quantity }], serial_ids: [id], settlement_mode? }`，不接受查询参数、客户端金额/成本/供应商或当前门店。普通批次最多100行，SN最多1000件，至少选一件；批次键须为 `event:正整数`，数量和SN ID为有效正整数，重复批次或重复SN返回400。普通数量与SN可混合选择，同一个SN不能用普通数量代替。

服务端复用上述原采购、完整付款链、原入库与当前余额的单连接只读RR快照，另重读所选实物及原采购正余额。普通批次必须为指定原采购/实际商品/授权当前店的普通库存且余量足够；SN必须仍在库并属于相同原采购、实际商品和授权当前店，其成本与原采购一致。SN表没有逐件用途：同一原采购/店内存在多个SN用途组时拒绝试算，不能猜实物用途。金额按原采购单价乘实际选中数量计算，零采购成本允许试算为0；不参考当前模板价格。并发移走、数量不足、来源/成本不符或用途歧义返回409 `PURCHASE_RETURN_SELECTION_CONFLICT`，缺历史原入库来源返回 `PURCHASE_RETURN_UNTRACKED`，其余账差沿用核对错误码。

选择解析和原批次分配的唯一实现为 `backend/src/utils/accessory-purchase-return.js`，当前由试算直接调用。仓储候选携带原实际商品/采购ID及SN在库状态，分配器逐行重新核验这些身份、当前授权店、原成本、批次用途、数量及候选去重；不只依赖SQL筛选。混入其他品牌商品、其他采购、越权店、已出库SN或未请求批次均拒绝。内部结果保留原批次事件ID及每件SN ID，按店铺/原事件排序、SN按逐件ID排序，输入顺序不改变归属或金额，也不修改输入快照；这些内部身份不扩大公开响应。分配器不持锁、不扣库存或登记资金，未来提交必须在原事务持锁后重读并分配，不能将本次只读结果直接用于写入。

响应为 `purchase_id/quantity/purchase_cost/total_amount/payment_status/latest_event_id/preview_only=true` 及 `data`；各行含 `row_key/store_id/store_name/quantity/usage_type/serial_tracking/serial_numbers`。省略 `settlement_mode` 时仅返回原采购价格试算，保持原只读接口行为；传入时额外返回 `settlement: { mode, payable_reduction, refund_amount, credit_amount }`，三个金额按整数分规划，仅所选归属可为非零。未付款只允许 `reduce_payable`；已付款只允许 `supplier_refund`（拟退款）或 `supplier_credit`（拟留抵后续货款）。非法值400，方式与重核的当前付款状态不一致409 `PURCHASE_RETURN_SETTLEMENT_CONFLICT`，不能用客户端付款状态或金额确定归属。零成本可返回零金额。上述值均为计划，不表示退款到账、应付已冲减或贷项已生成；不签发提交凭据、不占库存、不追加资金/库存流水、不清除写请求缓存。实际提交须重新持锁核对及落账，仍归T22。

仍要求两模块view及核对必要字段；另要求库存成本、用途和SN管理可见。请求包含SN时额外检查SN字段，隐藏SN仍可普通试算。页面普通数量和SN选择跨页保留，翻页/搜索/重读会废弃旧试算，重新核对清空选择；关闭、换单、撤权取消在途试算并清理草稿。已付款页面每次可选退款或留抵，未付款显示拟冲减应付；切换方式同步取消旧请求、清除旧金额，迟到响应不恢复。响应同时核验原付款状态、所选方式及三项金额归属。失败不丢选择，允许重新试算；只读接口采用POST承载有界选择体，统一API显式禁用自动写请求缓存失效。

`npm --prefix backend run migrate:film-services` 默认只读预览：在类型表增加兼容列 `film_enabled TINYINT(1) NOT NULL DEFAULT 0`，新增服务事实表 `customer_film_services`，订单ID唯一关联原 `sales_orders`，另保存客户、原资格销售ID（可空）、服务门店、办理人/实际创建人、耗膜量及业务/录入时间。订单/客户/手机销售/店铺/员工外键的整数类型从真实父列元数据核对，RESTRICT限制删除和更新；不建第二套库存、积分或客户表。不按名称回填、不补造旧服务；本次设备关联由后续模板匹配扩展迁移提供。

前置为既有类型、客户、手机销售、共同结算及商品库存结构。确认目标、停写及完整备份后才可用 `-- --apply --backup-file=/绝对路径/独占备份.json`；脚本先独占创建0600结构/原类型记录备份，再执行DDL，回读核对结构、原类型摘要及空服务表。DDL中断保留备份和部分结构，新备份可幂等补齐；字段、索引、前缀或外键规则冲突不覆盖。空结构回退使用 `-- --rollback --apply --backup-file=/绝对路径/回退备份.json`，任一旧启用标记或服务历史禁止回退及重建缺失结构；本次扩展列尚在时须先按扩展迁移保护顺序处理。基础迁移已于2026-11-14授权执行并回读，不能替代本次5列扩展；结构变更后重启后端释放公共结构缓存，显式配置角色权限及目标模板。隔离替身测试不代表真实MySQL业务验收。

### 手机详情办理与记录

角色授权入口为“权限管理 → 选择角色 → 页面权限”：综合查询“查看”对应 `query:view`，“贴膜”对应 `query:film`。这两项独立授权当前客户设备的免费/收费贴膜和最小服务历史，不要求商品管理查看、新增或赠送，不因此开放商品管理页面、普通商品出库或系统管理。客户关联、必要字段可见性、服务门店范围、适配及库存仍逐项核验；权限开关和操作日志统一显示“贴膜”。

综合查询手机模式在PC、平板及手机双击普通字段进入共用设备详情后，`QueryDetailContent → QueryDetailDialog → FilmServiceDialog` 提供“贴膜”；PC的成色、状态和备注继续保留各自专用双击入口。按钮使用 `query:view/film` 公共权限指令，处理函数重新核验；客户ID及姓名/电话必须来自当前关联，隐藏必要客户字段时明确提示，不按姓名或手机号猜关联。历史实时分页，分别显示累计服务次数与用膜量、每次时间、门店、办理人、商品及收费/免费原成交净额，不显示原手机购买店或采购成本；字段隐藏同时约束派生金额。关闭、切换客户身份或任一配件字段权限变化均取消旧请求，清理历史、资格及子结算，并按最新权限重读第一页；失败清空旧次数和历史，可重试，不能沿用旧资格办理。

客户详情的 `CustomerFilmHistory` 提供“查看贴膜记录”，点击后懒加载并复用同一 `FilmServiceDialog`，不复制服务历史或新增业务表。入口同时要求 `customers:view`、`query:view/film`，客户与配件模块姓名/电话均可见，且客户ID及姓名/电话有效；父详情关闭、切客或失去必要权限立即卸载。读取历史不自动办理；办理仍须从具体手机详情进入，不能在纯客户历史中提交。

贴膜查看不保留底部纯“关闭”；纯客户历史或没有办理动作权限时不渲染footer。手机详情可选择免费或收费，分别显示“确认免费贴膜”或“选择商品并收款”，必要资料、权限及免费服务门店未就绪时不能提交。公共 `MobileDialog` 处理顶部关闭；有办理表单时禁止遮罩关闭，提交中或结果未知时禁止关闭，子结算关闭约束沿用原流程。

免费在当前手机详情必选服务门店、填写实际耗量，并从当前型号的免费专用候选中选择具体品牌/颜色后提交。免费和收费候选使用专用 `GET /query/customers/:customerId/film-services/products?phone_id=...&store_id=...`，免费附加 `free_only=true`；服务端校验真实设备客户关联并确定型号，拒绝客户端扩大型号或适配范围，不返回采购成本，按启用模板、类型、适配型号及所选店可用普通库存过滤；提交事务再次核验当前手机客户关联、模板免费配置、适配、权限及库存。收费复用 `SalesGoodsCheckoutDialog` 和 `SalesGoodsLine`，固定当前设备及客户，展示当前型号适配且所选门店有库存的全部收费候选，不按免费专用开关排除商品；类型仅作分类。选定商品后进入窄版贴膜收银弹窗，只展示应收金额、当前可用积分、积分抵扣金额、人工优惠金额、实收金额、收款方式及必要的支付渠道，不重复展示商品、门店、客户、销售员、销售日期或交易流水号；实际收款可低于应收，人工优惠按“应收 - 积分抵扣 - 实收”计算，已选商品、客户、门店和当前办理人继续由上下文提交。手机号字段隐藏时摘要和提交按客户ID关联，不要求前端读取或提交手机号。贴膜动作授权允许所选适配商品收费或赠送，不扩展普通商品出库权限。试算和提交分别走 `POST /query/film-services/checkout/quote`、`POST /query/film-services/checkout`，继续复用共同结算控制器与事务；专用接口拒绝缺失贴膜资料、混售手机或冒用其他办理人。专用提交沿用统一API失效商品库存、客户、销售、查询及首页等相关缓存；两种办理成功均重读历史第一页，并将当前弹窗动作按钮锁定为“贴膜完成”；失败不伪造服务次数。

正式回归入口为 `backend/test/film-services.check.js`、`backend/test/film-service-history.check.js`、`backend/test/film-template-matching.check.js`、`backend/test/film-template-migration.check.js`、`backend/test/film-service-migration.check.js`、`backend/test/accessory-sale-options.check.js` 及 `frontend/tests/accessory-entry.spec.ts`、`frontend/tests/accessory-settings.spec.ts`、`frontend/tests/film-service.spec.ts`、`frontend/tests/customer-film-history.spec.ts`、`frontend/tests/sales-goods-checkout.spec.ts`。历史回归在内存SQLite执行实际仓储查询，覆盖当前设备真实客户关联、跨店记录、已退手机仍可查看办理、服务次数与耗膜量分计、原型号快照、客户隔离及分页；只移除不支持的行锁后缀，不验证MySQL锁和多连接隔离。实际执行结果统一登记T22。

## 商品销售与搭售

综合查询商品模式提供独立“商品销售”入口，销售管理不再提供独立商品开单；单台/批量手机销售底部“配件”可转到共同结算弹窗办理搭售或赠送。商品模式候选使用 `GET /query/goods/sale-options`（要求本页查看、商品查询及共享销售/赠送任一动作）；商品管理来源继续使用 `GET /accessories/sale-options`，严格按销售门店返回实际品牌商品及普通/SN数量，搜索与滚动可读取全部分页，字段隐藏不参与关键词或响应。SN按实物录入自动计数；综合查询商品模式的客户摘要、试算和提交分别使用 `GET /query/goods/checkout/customer-summary`、`POST /query/goods/checkout/quote`、`POST /query/goods/checkout`，复用既有结算控制器、服务和事务；商品管理及手机搭售保留公共结算入口，手机搭售只有综合查询商品授权时按商品子范围处理。赠送需独立权限，混合单逐条关联手机，只有一个公共备注；不改入库资料。接口参数、请求幂等和页面限制统一见[商品销售页面与候选检索](../guides/sales-transfer-transaction-standards.md#商品销售页面与候选检索)。商品明细积分抵扣、商品/共同手机退货、商品换货及正式商品工资保存/发放代码已接通；手机/整单积分抵扣尚未开放。相关来源账、售后及工资结构的云端迁移与真实业务验收边界统一见T22。

## 客户商品购买及赠送历史

客户详情新增只读 `GET /query/customers/:customerId/goods`，沿用 `QueryGoodsController → QueryGoodsService → QueryGoodsRepository`。认证后同时要求 `customers:view`、`query:view`、`query:goods-view`，服务层再次核验；只接受 `page/page_size`，分页分别上限100万页/100条。使用真实 `accessory_sales.customer_id` 参数绑定和原销售门店范围，不能用姓名/手机号推断归属；无绑定门店的普通用户保持空范围。COUNT和分页行共用既有只读一致性快照，不因客户在其他门店有消费而扩大可见范围。

## 综合查询商品模式

商品模式操作权限独立配置：

| 操作 | 综合查询权限（均需查看＋商品查询） |
| --- | --- |
| 查看、整单明细、凭证及售后历史 | `view`＋`goods-view` |
| 收费出库 | 再加 `goods-sell` |
| 赠送出库 | 再加 `goods-gift` |
| 退货 | 再加 `return-to-stock` |
| 换货 | 再加 `exchange`，换出商品另验销售或赠送动作 |

共享出库能力通过 `goods-permission.js` / `useGoodsPermissions` 解析来源，不反向授予商品管理页面权限；既有商品管理来源保持原动作。实际混合结算逐行核验，只有收费或赠送一项授权不能混用另一项；撤权清除在途请求和草稿。新动作由唯一能力清单派生，普通角色须明确授权，代码更新不自动修改角色。正式权限矩阵见 `backend/test/goods-permission.check.js`、`frontend/tests/goods-permissions.spec.ts`。


商品列表、详情、手机随单配件及售后历史由 `QueryGoodsService` 在公共连接租借入口内编排 `REPEATABLE READ, READ ONLY` 事务，仓储沿用传入的同一连接。单次请求内的COUNT/分页、原销售/已退量、SN/采购来源及售后头行/真实换货链读取同一快照；并发新销售或售后提交在下一次请求可见，不将不同时点的事实拼为一张单据。不使用行锁、提交写入或请求内DDL。正常/业务异常均回滚结束读取；配置或启动失败、回滚失败销毁连接，公共helper仍负责释放。分页之间、多个手机销售的独立请求之间不承诺共享同一快照，实际售后提交仍须在写事务重新核验原单。

`/query` 默认手机模式，具备 `query:goods-view` 才显示商品模式；进入商品模式仍须拥有 `query:view`。`QueryGoodsPanel` 复用原页面及商品字段权限，不创建独立权限模块。手机、平板支持公共表格双击详情，桌面双击及“详情”按钮均可打开同一原单。共同商品明细有未退数量且具备 `query:return-to-stock` 时显示“退货”，进入 `GoodsReturnDialog`，提交成功后实时重读；契约见[商品原单退货](../guides/sales-transfer-transaction-standards.md#商品原单退货)。商品模式不展示手机快捷入库/销售/导出动作；独立商品开单使用本模式“商品销售”，按本页商品销售/赠送权限办理。云端结构与真实业务验收仍见T22。

| 接口 | 参数及响应 |
| --- | --- |
| `GET /api/query/goods/filter-options` | 商品查询筛选选项，返回按 `basic_info.brand_name`、`basic_info.category` 字段权限裁剪的品牌和商品类型；要求 `query:view` 与 `query:goods-view`，不要求配件管理权限 |
| `GET /api/query/goods/product-name-options` | 可选 `keyword`（最多100字符；为空时返回最近成交的100个商品名称）、可选 `store_id`；返回当前账号授权销售范围内的成交商品名称，要求 `query:view`、`query:goods-view` 及商品名称字段可见 |
| `GET /api/query/goods` | `page/page_size`（默认1/20，单页最多100）、可选 `keyword`（最多100字符）、`store_id`、`sale_type=sale/gift`、`sale_operator_id`、`brand_id`、`product_name`（最多100字符，模糊匹配）、`category_id`、`start_date/end_date`（北京时间日期，包含首尾整日）；返回 `data` 记录及 `pagination`，未提供的筛选不限制。筛选字段隐藏时服务端拒绝对应参数 |
| `GET /api/query/goods/:id` | 按商品销售ID读取原单、`serial_numbers` 和 `batches`；不存在或超出门店范围统一404 |
| `GET /api/query/goods/:id/aftersales` | 按同一销售ID和公共分页读取售后数量/SN、退款/补款及积分变化；仅包含原店与办理店均获权的历史，缺表/字段明确返回409，不伪装为空记录 |

请求链路为 `query.js → QueryGoodsController → QueryGoodsService → QueryGoodsRepository`，复用统一认证/授权、门店范围和共享数据库连接。三个接口及服务均校验上述两项查看权限。未绑定门店不能查到记录；显式越权门店不会扩为全店。列表计数和分页使用相同筛选，SN通过存在性子查询匹配，避免逐件记录扩大销售数量。查询禁用缓存，筛选/翻页/详情使用 `useLatestRequest`；读取失败保留旧列表并提示，关闭或权限撤销取消旧请求。

销售记录来自 `accessory_sales`；共同单通过 `sales_order_items` 返回成交时商品资料快照、`sales_orders.order_no`、`order_id/order_item_id` 和关联手机 `sales.invoice_number`。`has_snapshot=0` 的旧出库明确标注“当前档案（原单无资料快照）”，不能把当前名称当成历史快照。综合查询展示、按日筛选和排序使用 `COALESCE(sale_time, created_at)`：新商品购买或赠送保存业务日期加提交时当前北京时间时分秒，贴膜购买或赠送保存提交时当前完整北京时间；`created_at` 保留数据库实际写入时间，旧记录缺少 `sale_time` 时回退读取它。金额、客户、原数量、销售员及其他资料读取原销售事实；新增 `returned_quantity/remaining_quantity` 从原销售关联 `sale_return/gift_return` 事件核对，不改原销售数量。金额界面称“实收”，不作为扣退货后的净收入；接口字段仍按原销售事实返回。`purchase_cost` 为原单保存的成本，界面称“成本”；旧出库可能没有真实批次成本，未知值保持NULL。

详情的来源批次读取原销售负数 `accessory_inventory_events`，按 `stock_in_id` 关联原采购批次及供应商，返回实际数量、采购单价、用途、入库员和日期。SN读取原销售/赠送事件，不按实物当前店铺重建历史；没有批次事实时显示空记录，不按当前主档供应商或进价补造。

共同原单详情内的 `GoodsAftersaleHistory` 独立分页读取已有追加售后表，展示每次退款/补款、原优惠追回/补退、积分处理量和账户变化、办理店、人、原因备注及两个时间，不把部分可见历史合计为全单净额。复用公共表格/编号/分页/支付/Loading/空态，失败可重试、关闭即取消读取；无共同明细的旧单不展示该区块。完整字段及未迁移边界见[商品售后历史查询](../guides/sales-transfer-transaction-standards.md#商品售后历史查询)。

字段脱敏使用 `query_queryview` 的 `goods` 子范围，用户字段接口读取键为 `query_goods`；角色字段配置入口为“综合查询 → 商品模式”，名称和排序跟随母菜单。未单独保存的角色逐角色兼容原配件限制，保存后与手机及配件字段独立；配置格式与兼容边界见[综合查询的手机与商品字段](../frontend/field-permission-guide.md#综合查询的手机与商品字段)。原字段ID保持：单号复用 `basic_info.sequence`，出库类型复用 `basic_info.usage_type`，销售时间复用 `time_info.created_at`，客户、成本、利润、数量、SN、店铺、备注等按原字段递归遮蔽，包含嵌套批次。数量隐藏时同时遮蔽已退量、剩余量；数量、单价或总额隐藏时同时隐藏可推导的金额和获得积分。这里的获得积分是该商品明细本次产生的积分，不是客户账户余额或历史累计总积分。隐藏字段不参加关键词搜索，隐藏门店、类型或日期时拒绝显式提交该筛选，避免通过命中结果反推数据。

## 资料边界

配件沿用项目公共数据库连接，专用表为十二张：`accessories` 保存商品模板及所属实际品牌商品，`accessory_stock` 保存门店汇总库存，`accessory_stock_in` 保存采购入库事实，`accessory_sales` 保存销售记录；`accessory_categories`、`accessory_units` 分别管理商品类型和单位，`accessory_compatible_models` 保存商品与已有手机型号的多对多关系。另有 `accessory_serials` 保存逐件 SN、状态及店铺位置，`accessory_serial_events` 保存入库、销售、赠送追踪，`accessory_transfers` 保存店间划拨，`accessory_purchase_payments` 追加保存采购付款登记与撤销历史。`accessory_inventory_events` 保存批次接续、入库、划拨和销售/赠送的数量与成本事实。不另建数据库或品牌、型号、颜色、供应商、门店、员工副本。

| 字段 | 契约 |
| --- | --- |
| `category_id` / `category` | 分类引用 `accessory_categories`，如手机壳、钢化膜、数据线、充电头；主表名称优先，原文本作为历史兜底。不引用手机型号充当分类；类型由设置页面维护 |
| `unit_id` / `unit` | 单位引用 `accessory_units`，如张、个、套、条；名称由设置页面维护，原文本作为历史兜底 |
| `brand_id` | 商品本身的实际品牌，引用公共 `brands` 的配件/两者范围；入库显示“品牌”，独立于适配品牌，可在选模板前后选择。模板新增/编辑不展示或提交，保留旧关联；未选品牌作为未指定品牌库存，不代表设备适配范围 |
| `template_id` | `accessories` 的内部所属模板关联；模板为空，按模板采购的新品牌商品关联根模板，使用独立商品 ID 记库存。HTTP 写载荷不接受客户端指定该字段 |

| `model_ids` / `model_id` | 多选适配机型只引用公共 `models`，关系保存在 `accessory_compatible_models`；`model_id` 保留首个适配型号供原接口回显。选择器按手机品牌加载完整型号，不受商品自身品牌限制 |
| `model_brand_id/name` | 通过已有型号关联品牌派生的响应字段，辅助回显，不作为额外写入字段 |
| `color_id` / `supplier_id` | 引用已有公共颜色/供应商。供应商引用按 `suppliers.business_scope` 校验；配件可选 `accessory` 或 `both`，旧配件保留原供应商关联 |
| `store_id` | 本次入库门店，未分配的剩余数量存入该门店；选项和后端写入均限制在认证用户可访问门店 |

商品类型、单位状态和排序由 `/accessories/catalog` 配件设置模块控制。当前云端已执行商品资料迁移，历史分类、单位按原文本精确初始化，不自动合并保护壳/手机壳、贴膜/钢化膜等名称。整批应付与付款历史已接入商品采购；批次用途、数量流水和出库成本见下文“批次库存流水与入库用途”，配件详情提供当前批次库存查询。门店汇总表不作为采购来源。

## 一个模板管理多种颜色

商品模板新增支持多选颜色，选中后逐色填写条形码，条码可空；公共名称、类型、适配型号、厂家型号、单位、零售价、备注等只填一次。提交沿用 `POST /accessories`，新增 `color_variants: [{color_id, barcode?}]`；最多100色，颜色必须有效且不重复，非空条码去除两端空格、长度不超过100且不能重复或占用其他商品条码。父模板不同时填写顶层颜色或条码。无颜色规格数组的原单颜色创建与编辑保持原契约。

新增关系表 `accessory_template_colors` 连接统一模板与各颜色采购根模板；每个颜色根仍是原 `accessories` 记录，实际品牌库存继续通过原 `template_id` 关联具体颜色根。统一父模板自身不采购入库，传其ID返回400 `COLOR_VARIANT_REQUIRED`。入库选择颜色后使用该颜色采购根ID，原批次、普通/SN库存、销售、退货和成本归属不变；条码查询直接定位具体颜色。不同颜色及品牌不合并库存，模板列表隐藏颜色根记录、统一展示一个入口，并允许按可见的颜色名称或条码检索父模板；分页数量与条件一致。

列表、详情及条码响应在原商品契约上追加 `color_template_id` 与 `color_variants: [{accessory_id,color_id,color_name,barcode}]`。模板详情须选择颜色后查询原批次、门店库存、SN和划拨记录，不以统一父模板的零库存代表整组库存。实际库存行继续显示自己的颜色。名称、颜色、条码沿用原字段权限递归脱敏，隐藏条码不发送嵌套条码字段，隐藏颜色禁止写入规格数组；认证、角色权限、JWT、CSRF、Loading、最新请求、通知和响应式表单沿用公共入口。

`PUT /accessories/:id` 的模板编辑与商品“编辑档案”均支持多选颜色、回显整组条码、追加颜色及更正条码；从某个颜色或实际品牌商品进入档案编辑，也可维护整组颜色。已保存颜色保留采购身份，当前不移除或替换。组内模板或商品档案编辑双向同步公共字段与展示快照；颜色ID保持各自身份，条码只同步对应颜色及其品牌商品。实际品牌、供应商和采购成本仍归实际商品；采购/销售数量金额、已付款和历史成本快照均不改。组父、颜色根及快照在同连接事务更新，失败整体回滚；停用/重新启用同步整组。原批次编辑识别品牌商品所属颜色、保留原商品ID及数量；允许的原入库更正若修改厂家型号，同步整组档案，先锁组父、再按稳定顺序锁全部关联颜色根，沿用原批次后续业务和付款保护。

旧单颜色模板编辑同样显示多选，原颜色和原条码回显；仅保留一个原颜色时沿用原单颜色载荷，不自动建组。追加颜色并显式保存时，复用原更新接口及已迁移关系表：同事务新建统一父入口，把原商品ID作为原颜色采购根关联，新增颜色使用各自采购根；原品牌子商品的`template_id`和全部交易ID不变，原库存不迁移或合并。必须保留原颜色；原来没有颜色时，界面明确提示首个选择颜色归属现有商品。扩色失败整体回滚，关联并发变化或锁冲突返回409，要求刷新重试。后续从顶部或模板/库存行内入库时，统一展示该模板的全部颜色及对应条码，各色分别填写数量、共用进价等资料；原批次更正只读展示所属颜色，不切换采购身份。颜色按商品模板关联，不把同一商品分类下其他模板的颜色合并。

表单按当前模板的颜色数量切换布局：无颜色或只有一个颜色时，入库数量在上方基本信息填写，条形码在上方只读展示，不显示下方“颜色库存”及重复颜色摘要；只有两个及以上颜色才展开逐色数量/SN与对应条码。单颜色SN仍沿用原SN录入和自动计数。顶部入库、模板行内入库与库存补货共用此规则；单颜色组父入口提交对应颜色采购根，已有品牌商品保留自身ID，不把采购写到组父。模板新增、编辑及档案编辑的单颜色使用普通条码输入，扩为多色后才逐色展示，切换布局保留仍选中颜色的条码；已建组的单颜色仍保存原规格关系，不改采购身份。

“颜色库存”区域按颜色展示条码与数量，普通数量为0至999999整数，0表示本次不入库，至少一色大于0；统一父模板初始各色为0，从具体颜色商品补货时该色默认1。供应商、实际品牌、店铺、进价、用途及备注共用，自动合计数量和采购金额，各色仍形成独立采购批次与应付。SN模式改为按颜色分别输入或扫码，每色数量自动计数；跨颜色重复SN拒绝，所有颜色合计最多1000条SN、999999件，采购合计金额小于1亿元。后端锁定颜色映射并重新核对同模板归属、实际颜色及公共采购条件，不接受其他模板、品牌子商品或重复颜色混入。隐藏颜色或必要采购字段不能办理，条码/SN等嵌套字段逐项拒写，回执逐批沿用原递归脱敏；采购金额隐藏时页面不显示合计金额。单色旧模板和原批次更正保留原数量及SN录入方式。未确认的整组请求同样由原Pinia/会话存储持久化，关闭重开仍冻结原内容，完整回执核对后才清理和刷新。

## API 与权限

库存/模板、候选及入库等受字段保护的入口使用严格字段读取；商品查询、随单凭证、共同结算、采购付款和售后沿用同一公共机制。权限查询或配置解析故障返回统一错误，不能按空隐藏字段放行。配件路由将已验证的配置仅保存在当前请求，后续拒写和响应脱敏共用，提交后不再重复查询字段权限。规则和正式故障回归见[字段权限后端边界](../frontend/field-permission-guide.md#后端边界)；此更改不新增字段、动作或数据库迁移。

`GET /api/accessories/options` 使用 `accessories:view`。返回最小参考字段的 `categories`、`units`、`brands`、`model_brands`、`models`、`colors`、`suppliers`、`stores`，不返回供应商银行/联系方式或员工敏感资料。供应商仅列出业务范围为配件或两者的启用记录；当前商品已有的旧供应商作为单项保留回显，后端不允许把手机专属供应商新关联到配件。

配件业务服务的 `DATABASE_ERROR` 返回 HTTP 500，并通过公共 `ApiResponse` 隐藏内部错误，不再误报为参数错误 400 或商品不存在 404。真正的商品不存在继续返回 404；业务校验失败保留原 400/403 语义。

设置页面使用独立模块 `accessories_accessorycatalogview`：`GET /api/accessories/catalog` 要求 `accessories-catalog:view`，新增分类/单位要求 `accessories-catalog:create`，编辑分类/单位要求 `accessories-catalog:edit`。页面按钮、路由守卫和后端接口使用同一动作；拥有配件库存模块权限不自动获得分类/单位维护权限。

入口位于配件管理页顶部的“设置”，内含商品类型、计量单位和仓库设置。路径和权限标识保持兼容。界面中的商品类型仍沿用 `category_id` / `category` 与 `accessory_categories`，仅统一显示名称。发布时还需将该模块注册到当前环境的 `modules`；只登记源码能力清单不会立即使既有登录会话显示入口。模块元数据固定使用实际路由 `/accessories/catalog`，避免扫描器按文件名生成错误地址。2026-11-12 已通过公共 `ModuleManagementService.registerModule` 定向完成云端注册并回读验证；按[页面权限能力规范](../frontend/permission-capability-standards.md#修改或移除功能)补齐管理员角色的 `menu_view/view/create/edit`，普通角色授权未变。重复注册未增加权限。普通角色需要在权限管理中明确授予商品资料的相应动作；既有会话刷新权限或重新登录后生效，不得用父模块权限兜底。

- `brand_id`：适配手机品牌；未传时不查询全库型号，`models` 为空。
- `accessory_id`：编辑/扫码补货回显用。服务端根据原档案带回当前停用引用；其他停用项不进入新增候选。
- 商品品牌、适配机型、颜色、分类、供应商及门店的隐藏权限分别清空对应整个选项组；适配手机品牌从属于适配型号字段。
- 参考选项统一经前端 `services/reference-options.ts` 的 `getAccessoryEntryOptions` 读取。打开表单实时加载；型号按品牌查询，并丢弃旧请求；加载失败禁止提交。

`POST /api/accessories/stock-in` 使用独立 `accessories:stock-in`，`PUT /api/accessories/:id` 沿用 `accessories:edit`。`product_model` 沿用历史权限标识 `basic_info.specifications`，权限管理中名称改为“配件型号”（该标识不是数据库列），确保原角色的隐藏设置继续生效；读响应脱敏、写入拒绝及前端提交白名单保持一致。

入库创建商品时保存配件型号；扫码/ID 补货仅引用原商品，不能顺便覆盖原商品档案或公共资料。新选公共资料必须存在且启用，编辑可保留原停用引用，也可清空可选关联。在具体适配品牌之间切换仅刷新候选型号，保留已选的跨品牌适配关联；选择或清空适配品牌为“通用”时清空具体型号关联，表示全部品牌、全部机型均可使用。商品自身品牌与适配品牌独立，不根据适配品牌回填商品品牌。

入库“商品名称”复用 `GET /accessories?mode=templates` 的远程分页检索，不把首批20条当成全部候选。商品列表的关键词按空白分词，多个词须共同命中同一商品的可见名称、类型、厂家型号、颜色或适配型号等字段；名称/型号比较复用公共 `normalizedModelSql`，忽略大小写、半角/全角空格及连字符差异，条码继续保留其编码比较语义。商品型号或条码中的 `%`、`_` 和 `!` 通过公共 `escapeLikePattern` 按字面匹配，不扩大为SQL通配符。COUNT和分页使用相同条件，隐藏字段不参与检索。模板与库存列表共用该匹配规则，前端不再二次过滤接口命中结果。

入库候选按商品类型分组，主行保留名称，辅助行展示允许查看的厂家型号、颜色、适配型号、零售价/单位和默认SN管理标记，以区分同名规格；根模板不展示虚构的实际品牌或批次库存。查询时只展示当前命中项，已选资料独立保留回显。分页保留关键词，滚动及“加载更多”均可继续访问全部结果；下一页失败保留已有候选，重试同页，成功后才推进页码，并按商品ID去重。失败提示与无匹配分开，取消/旧响应不回填或关闭新Loading。加载及结果挂载引起的浮层重复可见事件不能重新清空候选或覆盖关键词。布局复用公共 `el-select` 与表单浮层，支持手机换行。正式回归见 `backend/test/accessory-inventory-read.check.js`、`frontend/tests/accessory-entry.spec.ts`；隔离浏览器入口为 `node frontend/scripts/test-accessory-stock-correction.mjs`，追加 `--template-search-only` 可单独验证名称检索。使用内存候选并阻断业务和外站请求，不代替云端MySQL、已登录整页或真机验收。

商品模板在配件管理单独创建；后端仍兼容首次入库同时建商品，当前表单从已有模板入库。单独创建调用现有 `POST /api/accessories` 和 `accessories:create` 权限，保存商品资料及适配关系，不创建采购记录或门店库存。模板入口不展示供应商、进价、数量、入库门店和入库员字段；实际到货从入库入口选中模板，填写实际品牌、当次供应商、进价、数量和门店。

顶部及空态入口统一显示“商品入库”，入库弹窗同名。在“商品名称”下拉检索模板，按类型分组，名称和辅助规格按上述候选规则展示；使用服务端检索及滚动加载（每次20条），底部显示已加载数量和总数，并提供“加载更多”或失败重试。选中后按ID读取详情并自动填充只读商品类型、配件型号、颜色及销售价，保留本次供应商、实际品牌、进价。模板/库存行内入库固定当前模板，不提供切换；顶部入库可按名称搜索。公共最新请求工具丢弃旧搜索/详情响应，候选文案和回填遵守字段权限，停用模板不可入库。

商品入库、模板新增/编辑、档案编辑及原批次更正统一使用公共 `tf-dialog-body-flush` 将正文四周外层留白归零，卡片内部保留公共控件间距；基本信息、可选SN录入及备注使用 `tf-query-modal-section` 和紧凑标题，卡片间距由公共分区令牌维护。各模式的字段、修改前后对照及独立提交规则不变。公共分区背景与正文使用成对的弹窗颜色令牌，适配明暗主题；SN工具及底部动作复用公共弹窗按钮尺寸。隔离浏览器同时断言正文零内边距、卡片间隔、标题高度、文字对比度、按钮公共尺寸/颜色及窄屏无横向溢出；追加 `--page-actions-only` 单独检查详情、划拨、设置TAB及类型/单位新增编辑，不提交真实业务。

入库基本信息按“供应商、品牌、商品名称、店铺、商品类型、配件型号、颜色、条形码、进价、销售价、入库总数、入库员、入库用途、SN管理、入库时间”排列；SN模式隐藏入库总数，两个及以上颜色时将颜色、条形码和入库总数移到下方“颜色库存”逐色填写、合计展示。电脑常规字段每行四项、平板/手机两列；入库时间电脑半行、平板/手机整行，完整显示秒级时间，隐藏字段不留空列。适配品牌、适配型号、单位、状态、预警值由模板控制，不在入库显示。新商品先创建模板再入库，后端首次入库建商品能力保留。模板新增/编辑仍保留完整资料及四列布局，不引入采购信息。

## 商品库存与模板组合筛选

`/accessories` 的商品库存、商品模板TAB共用公共 `UnifiedSearchPanel`，按“商品名称、商品类型、品牌、适配型号、颜色、状态”展示，名称与品牌表头使用相同文案。状态是颜色之后的独立筛选项，不堆叠在名称输入框下方，也不放到列表标题区；两个TAB都提供全部状态/启用/停用，库存默认启用、模板默认全部。商品名称继续沿用原 `search` 多关键词模糊检索及可见条码/型号匹配；类型、品牌、颜色通过 `getAccessoryEntryOptions` 全量加载并使用公共排序，不截取当前页记录作为候选。适配型号为独立文本检索，不以商品品牌误作手机品牌，不预加载全库手机型号；选项加载失败可显式重试。

列表复用 `GET /api/accessories`，在原 `category`、`brand_id`、`model_id`、`search` 等条件上增加 `model_name` 和 `color_id`。`model_name` 最多200字，使用公共型号标准化和LIKE字面转义，匹配直接型号及多型号关联的品牌/型号，忽略大小写、空白与连字符；输入“通用”只匹配没有直接型号和多型号关联的商品。`color_id` 必须为有效正整数，匹配库存商品继承的模板颜色；多颜色模板按其包含的颜色命中父入口。品牌库存按自身 `brand_id` 筛选；模板没有固有商品品牌时，通过授权门店中关联的实际品牌商品（含多颜色采购根的品牌商品）匹配，不泄露其他门店的品牌关联。各条件以AND组合，COUNT和分页共用同一筛选与只读快照，不修改库存。

颜色、适配型号、状态分别沿用 `basic_info.color_name`、`basic_info.model_name`、`status_info.status` 字段权限，隐藏控件不回传条件，后端在查询前拒绝隐藏字段筛选；没有新增动作权限。选择/清除条件、回车及搜索均回第一页；重置清空文本/类型/品牌/颜色条件并恢复当前TAB的默认状态，切换TAB同样重置，刷新保留当前筛选并重读参考资料。布局、展开、按钮和加载复用公共入口。正式行为回归为 `accessory-management.spec.ts`、`accessory-inventory-read.check.js`、`accessory-controller.check.js`；隔离浏览器运行 `node frontend/scripts/test-accessory-stock-correction.mjs --filters-only`，只使用内存接口，不替代真实MySQL及物理设备验收。

## 商品模板管理与默认零售价

`/accessories` 内分为“库存查询 / 商品模板”两个展示页签，共用同一商品主档及 `accessories:view/create/edit/delete` 权限，不建立第二套模板表或权限模块。“商品模板”默认查询全部状态，包含未入库与已停用的模板；顶部新增商品模板，行内编辑、入库和删除。启用模板可直接按商品 ID 补货，不要求先有条码。编辑可调整资料、适配机型、默认零售价及启停状态，采购供应商和成本不随模板编辑提交。删除沿用现有软删除：仅停用模板，保留库存、采购和销售记录；确认框明确告知含义，停用后可编辑恢复启用，不执行物理删除。

条码在模板编辑中可修改或清空，空值存为 NULL；服务端去掉前后空格、限制为文本且最多 100 字符，重复检查包含停用模板。商品内部 ID 保持不变，库存和交易继续关联该 ID，历史采购记录的扫码文本不被改写。条码输入及提交继续受 `basic_info.barcode` 字段权限控制。编辑回填的商品类型、颜色、单位、品牌、供应商及型号引用统一转为数字 ID，与公共选项值匹配，避免云端字符串编号在下拉框中显示为数字。

新增和编辑弹窗复用公共标签置顶表单与 Element 网格，基本信息按“商品名称、商品类型、适配品牌、适配型号、配件型号、颜色、单位、零售价、预警值、状态”排列。适配字段并入基本信息，不再单列适配卡片。电脑端四列，平板两列，手机常规短字段两列、名称整行；状态和SN管理使用公共开关，隐藏附加的开启/关闭文字，保留字段及无障碍名称；新建状态默认开启，编辑保留原值。模板条形码与商品照片并排放在基本信息之后，入库模式不展示这两个字段。控件尺寸、标签、间距及弹窗外壳继续由公共实现控制。

条形码支持手动输入或扫码，以字符串保存并保留前导零。模板新增/编辑只保留条码输入，不展示检索按钮或额外保存说明；录入及回车不自动查询，点击底部创建/保存时随模板提交，由后端执行条码唯一性校验。入库模式通过可搜索的商品名称选择具体模板并回填资料，不再展示条码检索区。未填写条码时不发起查询，也不生成虚构条码；后续扫码使用保存的条码识别商品。

模板新增/编辑不展示或提交实际“配件品牌”，保留旧 `brand_id`；新增/编辑保留“配件型号”（`product_model`），与适配型号分开。已移除“配件规格”输入和 `specifications` 数据库字段。“适配手机品牌”改为“适配品牌”，未选择显示“通用”；该选择目前仅筛选适配型号，选择苹果等品牌后加载对应机型，单选品牌而不选型号不会单独保存品牌关联。入库“品牌”为实际商品品牌，可独立选择，不读取适配品牌，也不被模板旧品牌回填或锁定；配件型号统一读取模板；普通补货选定模板后只读展示型号，不覆盖模板资料，切换模板也不保留上一模板型号。模板编辑及库存“编辑档案”双向同步全部档案字段；原入库更正显式提交配件型号时，在原更正事务内同步根模板与同模板历史采购/共同销售展示快照，失败整批回滚、幂等重试不重复同步。原入库备注仍是采购批次备注，不改模板备注。库存采用下述模板与实际品牌标识，不能通过补货覆盖历史品牌。

“适配品牌”提供显式“通用”选项；选中或清空为通用会清空已有具体型号，型号框禁用并显示“通用”，表示全部品牌、全部机型。此时无需关联全部手机型号。“适配型号”支持多选；未选择型号时，表单、列表和详情显示“通用”。保存仍提交空型号关联（`model_ids: []`、`model_id: null`），不创建虚构型号或关联全部手机型号。

模板 `sale_price` 是商品默认零售价，模板表单、列表和详情显示“零售价”，采购入库显示“销售价”，与采购供应商无关。新建模板或首次入库同时建商品时可填写；金额必须非负、小于 1 亿元且最多两位小数。补货检索到已有商品后只读展示当前模板售价，请求不携带 `sale_price`，本次只保存供应商、采购进价和数量等入库事实；服务端按已有 ID 或条码识别商品，不以补货载荷覆盖模板价格；新建实际品牌商品同样读取已锁定模板的售价，不使用客户端提交的售价。旧调用携带售价也不改变已有模板或产生批次售价。调价使用模板编辑接口，仍受编辑动作与售价字段权限控制。

列表通过服务端分页/检索加载，不能只在首次取得的 50 条记录中本地搜索。`GET /api/accessories` 的 `page/page_size` 对应实际分页，单页最多 100 条；`status=all` 查询全部，`0/1` 查询停用/启用，省略时仍默认启用。状态字段隐藏时禁止显式状态筛选，界面也不提供该筛选。搜索覆盖可见的名称、条码、分类、配件品牌、适配型号及配件型号，隐藏字段不参与搜索；关联 ID 和适配型号名称随所属字段一起脱敏。联合检索显式统一为 `utf8mb4_unicode_ci` 比较，兼容云端新旧资料表排序规则差异，不修改表结构。切换页签、筛选和翻页复用公共最新请求工具，写入成功后禁用缓存重新加载当前列表。

销售实际成交价由销售单的 `unit_price` 独立保存，修改模板不改历史采购或销售价格。独立商品销售及混合销售已接入共同结算；销售改价/作废和工资等完整流程仍归T22后续阶段，不能改模板后重写成交事实。

## 模板与实际品牌库存

`accessories.template_id` 区分根模板与实际品牌商品，不新增品牌或模板副本表。顶部商品名称候选和模板管理使用 `GET /api/accessories?mode=templates`，仅列根模板；库存页使用 `mode=inventory`，仅列授权门店已有库存记录的实际商品（包括已售完为零的记录），不能因其他店有记录而出现在当前库存列表。省略模式列共享根模板和授权门店库存商品，非法模式返回 400。模板页不展示实际品牌列。

本次云端已执行 `migrate:accessory-brand-variants -- --apply --backup-confirmed`：增加可空 `template_id` 和 `uq_accessories_template_brand (template_id, brand_id)` 唯一索引，不回填或重编号历史商品，不改库存、采购或销售记录。旧商品作为根模板保留，入库实际品牌与旧品牌一致时继续使用原 ID；其他品牌建立子商品。同模板同品牌更换供应商仍复用同一个实际商品 ID，每次供应商、成本、数量及操作员单独记入 `accessory_stock_in`。未指定品牌通过根模板锁和 NULL 安全比较复用，不把“无品牌”解释为适配通用。

入库事务先锁定根模板，核对启用状态与实际品牌范围，再查询/新建品牌商品，和采购单、门店库存一起提交或回滚。同模板并发请求由根模板行锁串行化，实际品牌唯一索引防止重复。客户端的名称、售价、适配等资料不能覆盖已存在模板，也不用于构造新品牌商品的共享资料。停用模板会令所有所属品牌商品读取为停用，不能继续采购/销售。

### 库存读取、预警与类型统计

## 批次库存流水与入库用途（2026-11-13）

采购入库新增 `usage_type`，`sale` 为收费、`gift` 为赠送，旧客户端省略时默认收费。它属于本次采购批次，切换模板不覆盖；模板新增/编辑不展示或提交。入库表单使用原公共四列布局和字段权限 `basic_info.usage_type`，隐藏用途时禁止入库，后端写入同样拒绝越权字段。备注仅接受文本，最多1000字。该字段保存于批次入库事件，不另复制到模板或供应商。

新增追加表 `accessory_inventory_events`：保存实际商品、当前门店、原 `stock_in_id`、单位采购成本、用途、SN/数量模式、事件、数量增减及认证操作员/北京时间；出库关联 `sale_id`，划拨关联 `transfer_id`。事件为 `stock_in / legacy_opening / transfer_out / transfer_in / sale / gift`。新入库采购单、门店加库、SN和数量流水同事务提交；划拨追加双店负/正事件，保留原采购、成本及用途，不重复形成应付。

普通数量库存按原采购时间/批次先进先出；指定SN按其真实采购来源及逐件成本分配，不能占用普通库存或其他SN批次。销售成本为各分配数量乘实际进价合计，销售记录 `purchase_cost` 为本次总成本，利润为成交总额减总成本；不读取商品主档最新进价倒算。2026-11-15复核现行分配器：入库用途只记录来源及流向，不限制后续收费或赠送；两种用途及历史未分类库存均可按实际销售方式出库，不另增“双用途”批次。赠送仍独立鉴权，原批次用途和真实成本保留。正式回归见 `backend/test/accessory-inventory-events.check.js` 的收费/赠送共用库存用例；共同订单、积分和提成沿用[共同结算契约](../guides/sales-transfer-transaction-standards.md#手机与商品共同结算)，真实业务验收及其余边界以T22为准。

事务先锁根模板、门店库存和SN，流水余额使用当前锁定读，避免默认可重复读隔离级别下，等待根模板锁之前建立的旧快照漏掉其他请求已提交事件。保留零余额批次，用于区分从未接续与已经清空；已有流水与汇总不一致时返回 `409 INVENTORY_LEDGER_CONFLICT` 并整单回滚，不自动补差。

### 历史库存接续

只读核对发现旧采购合计与现存量不能直接对应，不能按旧入库单反推剩余批次。迁移不回填真实期初、不改数量。首次涉及该商品门店的入库/划拨/出库时，在同一事务按锁定现存量追加 `legacy_opening`：普通量来源和成本为NULL、用途 `unclassified`；SN只保留已有可核对采购关联及逐件成本。汇总少于在库SN数时拒绝操作，包含汇总为零的异常情况。

历史普通商品仍可流转，未知成本在后续划拨/出库保持NULL；若同一次出库混有未知成本，本次总成本及利润均为NULL，不按0成本计算，也不猜测最新进价。调用方展示和提成必须识别“待核对成本”。历史来源核对和调整仍属于 T22.10，不补造供应商应付。库存详情另提供下述只读批次余额，不把原采购数量当成剩余库存。

### 当前批次库存查询

`GET /api/accessories/:id/batches` 沿用 `accessories:view`，只读返回该库存商品，或模板及其实际品牌商品，在授权门店中的正余额。接受 `page/page_size`（默认1/20，最大页大小100）及可选 `store_id`，拒绝其他参数、越权门店和非整数输入。前置库存流水/SN结构缺失返回409，不在请求内迁移。

`AccessoryService → AccessoryInventoryRepository` 在同连接只读 REPEATABLE READ 事务内核对商品、门店汇总、批次余额及在库SN总数，再读取总数与分页；读取结束回滚释放快照，不加库存写锁、不调用 `ensureBalance`，也不追加 `legacy_opening`。批次身份继续为“实际商品＋当前门店＋原入库单＋原成本＋用途＋SN方式”。保留零余额参加核对，列表只展示正余额；负批次、余额/门店或SN总数不符、采购来源关联丢失及无门店汇总的孤立流水拒绝返回，须人工核对差异。

响应 `data/pagination`，行含稳定 `row_key`、实际商品ID、当前门店、实际品牌/厂家型号、原批次号、原供应商、原采购单价、用途、管理方式、剩余数量、原入库时间及入库员。来源标记 `source_status=purchase/legacy/untracked` 分别表示已关联采购、已接续但来源待核对、尚无流水的历史现存量。历史未知成本保持NULL；未接续行不猜测SN/普通构成、用途、供应商或采购日期，不使用商品主档最新成本/供应商倒填。原采购内部ID不透传。供应商名称按采购快照优先、旧单才取原关联当前名称，品牌名称仍沿用商品原关联；采购金额与日期来自原入库事实，后续采购退货须另核原单及可退数量，不能直接以本列表作为退供授权。

控制器复用严格公共 `FieldAccessService`。门店或数量隐藏时整个查询拒绝，防止分页/正余额行反推；其他字段沿用配件字段映射递归脱敏，原进价、供应商、批次号、用途、SN方式、品牌、型号、时间及人员各自受控。来源核对标记只表达流水完整性，不授予成本或供应商资料权限。

批次查询的商品及门店编号在服务输出边界复用 `validId` 校验后统一为数字，拒绝空值、脏值及越界编号；云端MySQL保留BIGINT字符串的全局配置不变。金额与数量继续按既有 `number|string` 契约保留原精度，控制器字段脱敏及内部采购ID剔除仍在输出前执行。

前端 `AccessoryBatchStock.vue` 嵌入原配件详情，使用公共表格、编号、分页、Loading、错误重试及手机双击 `RecordDetailDialog`。读取失败通过公共 `getRequestErrorMessage` 显示服务端或网络的具体原因，只有确实账差时才显示库存核对原因；成功响应格式不完整仍拒绝展示，重试成功清理旧错误。切商品、字段授权变化、撤权或卸载取消旧请求并清除原明细；末页因库存变化消失时重读有效页。请求无缓存，不新增路由/权限模块/数据库表，不自动调整库存或采购应付。

## 商品库存盘点

商品库存页“当前批次库存”提供独立的“盘点”操作，用于修正普通数量采购批次在当前门店的实物结存。盘点数量允许为0，必须填写原因；勾选“含零库存批次”可继续查找普通数量有效采购的零结存批次，默认列表仍只显示剩余库存。服务端按批次流水重新核对门店范围，并在同一事务中只调整 `accessory_stock.quantity`，追加原批次 `stock_correct` 流水和 `accessory_inventory_adjustments` 审计记录。采购累计入库、累计出库、销售事实、历史销售成本和采购应付不被改写。相同数量只返回无差异结果，不生成空审计流水。

操作路径为“商品库存 → 商品详情 → 当前批次库存 → 盘点”；手机端双击批次行，在详情底部点击盘点。填写当前门店该批次的实际数量及原因后确认，成功即重读批次、店铺库存和主列表，并同步已打开详情中的总库存、剩余数量。盘点为0后可勾选“含零库存批次”再次定位该批次。它与“编辑原入库”独立，不用于修改采购数量或进价。

SN逐件批次暂不支持数量盘点，应先逐件核对串码；来源为历史未接续或流水账实不一致的批次也会拒绝并提示先核对差异。`POST /accessories/:id/inventory-adjustments` 只接受 `request_key/row_key/expected_quantity/counted_quantity/reason`，数量复用公共完整整数校验。请求使用32位幂等键，重试返回原盘点前后数量；提交时当前结存必须等于 `expected_quantity`，否则409拒绝，防止覆盖期间发生的销售/其他盘点。操作者、当前门店、批次、原因和差额均写入审计，字段权限与后端 `accessories:edit` 一致，手机端在批次详情底部提供同一入口。

## 商品原批次返库事务基础

`AccessoryService.returnSaleStock` 是供售后调用的内部事务能力，不独立开放HTTP接口。[商品原单退货](../guides/sales-transfer-transaction-standards.md#商品原单退货)已在同一事务接入原单/权限校验、退款/补款确认、积分与返库凭据；本方法不提交事务，不删除或改写原商品销售。手机返库、换货与工资冲回仍待接入，共同手机单旧退库保护继续保留。仓库 `total_out` 显示“累计出库”，包括赠送，返库不抹掉累计出库，也不增加采购 `total_in`。

普通商品按原销售出库事件的分配顺序逐批返还，保留 `stock_in_id`、采购成本、收费/赠送用途及数量/SN方式。原收费库存转赠送后退回仍是原收费用途；历史未知成本仍为NULL。原数量/成本与批次不守恒、缺流水、重复/超额退回或接收店汇总漂移返回409，不按当前模板进价或旧采购单猜测返库。停用模板仍允许核对原单返还，不因此重新开放销售。

SN必须仍属于原销售且为 `sold/gifted`；按其真实采购来源返还，恢复 `in_stock` 并清除当前 `sale_id`、保存接收店，追加 `return` SN事件关联原销售。原事件保留；已退回或再次销售的SN不能再次退旧单。内部能力允许选择授权且启用的接收门店，原销售门店也必须在服务端授权范围内；不改变跨店贴膜等业务规则。

库存汇总只增加可用 `quantity`，不增加采购 `total_in`、不抹除累计 `total_out`，不形成新采购应付。退回数量可从返库事件核对；重新销售或划拨继续复用原库存流水及FIFO。原商品、根模板、销售、门店汇总和SN按统一连接锁定，重复请求返回原回执，不因后续别笔退货改变原回执的剩余量；任何后段资金/积分/日志错误均须外层回滚，不能只提交返库。

在原 `accessory_inventory_events` 扩展 `sale_return/gift_return`，新增三个可空字段：`source_event_id` 指向原负数出库事件，`return_key`/`return_hash` 保存本次售后分项的请求标识及参数摘要。按原事件与请求键建立唯一索引并按原事件建查询索引；键使用区分大小写的ASCII规则。返库写正数数量，同一原出库累计不得超过原数量；保留所有旧事件，不另建一套库存。完整售后单据后续通过分项请求标识关联，不允许客户端脱离售后单单独改库存。

### 整单原成交明细

商品销售详情新增“整单明细”，与手机销售详情共用只读组件。对应接口 `GET /query/goods/:id/order`、`GET /query/sales/:saleId/order`，复用本域QueryGoods链、同连接只读快照及 `query:view`、`query:goods-view` 查看权限。完整读取原共同单；原手机/商品客户、门店、销售员工和金额不一致时拒绝，原交易全退后仍可查看原记录。商品SN/用途/积分及现金入账分别展示，不并入后续换货或退款。整单与手机随单凭证共用原快照赠品未退约定解析，区分未记录和明确零元，按原数量展示原约定总额；不计实收、不表示已扣款，随用途/数量/单价/总额同步脱敏，坏约定拒绝出具完整凭证。字段按手机/商品分别严格脱敏、共享头取交集、隐藏资金合计保护及正式回归见[整单明细](../business/sales-receipt-standard.md#整单明细)。无需新增表或迁移，已有共同结算结构未升级的云端不因本查询接入自动可用。
