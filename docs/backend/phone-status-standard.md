# 设备状态统一规范

## 有效状态

设备对外展示和筛选使用“有效状态”，不要直接把 `phones.status` 和业务标记拼接在页面中：

| 数据状态 | 业务标记 | 有效状态 |
| --- | --- | --- |
| `sold` | 任意 | `sold` |
| `reserved` | 任意 | `reserved` |
| `in_stock` | `is_preordered = 1` | `reserved` |
| 其他状态 | 任意 | 原状态 |

已售优先于预订标记，避免历史数据残留 `is_preordered` 时仍显示为预订。

## 代码入口

- 后端：`backend/src/utils/phone-status.js`
- 前端：`frontend/src/constants/phoneStatuses.ts`

后端查询使用 `getEffectivePhoneStatusSql('p')`，Node.js 数据处理使用
`getEffectivePhoneStatus(status, isPreordered)`；前端展示使用同名函数或对应的
`getEffectivePhoneStatusLabel`、`getEffectivePhoneStatusClass`。

## 销售记录有效性与当前归属

`phones.status` 表示设备现状，`sales.status` 表示一笔销售是否仍有效，不能互相替代。共同售后需要保留原销售用于追溯；当前销售查询统一复用 `backend/src/utils/sale-status.js`：

- `getActiveSaleSql(alias)` 只接受历史 `NULL`、`pending` 和 `completed`，排除 `cancelled` 及未知值。保留 `pending` 是兼容现有未取消销售口径，不表示它已经完成收款，也不能直接作为免费贴膜等已完成购买资格。
- `getLatestActiveSaleIdSql(phoneAlias, saleAlias)` 先按销售主键ID倒序取最新一笔，再检查上述状态；若最新一笔已取消，不回退到更早完成的记录；不使用可编辑销售时间或可能相同、倒置的创建时间决定当前归属。表别名经公共标识符校验，不接受外部SQL片段。
- 综合查询列表、分页、统计和销售员筛选使用同一笔当前销售；全部取消时客户和销售门店为空，门店回到设备当前入库/接收门店。库存详情、维修和补贴设备检索、手机编辑及再次销售校验沿用该口径。
- `GET /query/statistics` 的 `peer_transfer_count` 和 `supplier_proxy_count` 分别按当前调货和划拨设备状态计台数，复用综合查询统计的门店和筛选条件。字段权限见[综合查询的手机与商品字段](../frontend/field-permission-guide.md#综合查询的手机与商品字段)。
- `in_stock_new_count` 和 `in_stock_used_count` 分别按在库设备的全新和二手成色计台数，沿用 `in_stock_count` 的有效库存状态、门店范围和筛选条件。成色缺失的历史设备只计入在库合计。
- 综合查询未选择状态时，`new_count` 和 `used_count` 仅统计有效已售设备中的全新和二手数量，二者合计为成色已知的已售设备数。选择具体状态后，三个统计字段随当前状态筛选联动，分别表示该状态的成色已知合计、全新和二手数量；调货和划拨仍由独立汇总字段展示。
- 退货来源与共同明细必须通过真实 `sale_id` 关联；不能仅因同一 `phone_id` 曾有共同订单，就把后来的独立销售关联到旧单；按真实销售ID找到的共同明细即使手机ID或类型错位，也必须继续保护并拒绝核对，不能降级独立销售。`currentPhoneOrder` 用于当前交易编辑/退库保护；永久删除继续通过 `phoneOrder` 检查全部历史共同明细，不能删除已取消的原单依据。

客户管理列表的手机购买次数、消费金额和最后购买时间由同一份未取消销售聚合，最后购买时间排序也读取此聚合；客户活跃、价值、留存及消费偏好统计排除已取消销售。历史购买列表仍保留原单；H5历史金额、业务时间读取原 `sales.sale_price/sale_time`，时间缺失保留NULL，不读取已被返库清空或再次销售覆盖的设备售价/时间。不得把原单列表合计当作当前净消费，或把这些手机统计当成商品/资金的全站净额报表。

工资待计算销售和明细复用当前销售，避免相同创建时间产生重复行；这不实现已发工资的跨月冲回。当前共同手机售后仍未开放，此处只统一读取与保护边界，不自动取消销售、返库、改积分或调整客户存量统计字段。单号占用、积分来源、原商品/供应商/收款追溯必须保留历史，不使用有效销售条件过滤。

正式回归：`ENV_FILE=test/missing-unit-env RUN_DB_TESTS=false node --test backend/test/sale-status.check.js`。用例通过Node.js 22内置SQLite执行仓储SQL的查询、聚合及窗口行为，仅移除行锁后缀并提供测试日期函数，不验证MySQL行锁、多连接事务或真实业务退货。

## 规范存储与兼容输入

- `phones.status` 的可售状态只存 `in_stock`；`available` 是历史/外部来源别名，不是新的业务状态。
- 状态名称、搜索词及外部同步值统一经 `normalizePhoneStatus` 转为规范值；状态搜索通过 `isPhoneStatusAlias` 识别，路由不得各自维护映射表。
- 有效状态 SQL 由 `getEffectivePhoneStatusSql` 统一生成，兼容读取历史 `available`，并优先保留 `is_preordered = 1` 对应的 `reserved` 语义。
- 新写入和跨库同步必须归一化后再持久化，包括设备编辑接口；用户界面仍显示“可售”，不展示“可用”作为一个独立状态。前后端共享状态工具都将 `available`（不区分大小写、忽略首尾空格）映射为 `in_stock`。
- 2026-09-28 对当前本地配置的远程数据库执行只读状态分布检查：`phones.status` 中 `available`（忽略大小写与首尾空格）为 0 条，当前值均为规范业务状态；`phones` 表不存在 `sale_status` 列，因此未执行数据库更新。
- 若未来数据库审计发现旧值，应先备份，再仅将 `LOWER(TRIM(status)) = 'available'` 的设备状态更新为 `in_stock`，核对变更数后继续部署；禁止全表替换状态字段。

## 预订与销售

- 匹配预订：保留 `status = 'in_stock'`，设置 `is_preordered = 1`，表示设备仍在库但已被预留。
- 普通销售：不能销售 `is_preordered = 1` 的设备。
- 预定交付：销售页、库存页和预定页都可以发起出库；进入销售表单后必须同时匹配预定单、预定客户和匹配设备，客户信息不可改为其他客户。
- 销售成功：设置 `status = 'sold'` 并清除 `is_preordered`，同时完成预定单。

## 租赁与买断

- 租赁状态由租赁合同流程维护，不允许库存、销售或综合查询的通用设备编辑直接设置或解除 `rented`。
- 按天租赁创建合同后将设备状态设为 `rented`；归还操作由租赁管理完成，并在归还成功后恢复 `in_stock`。
- 到期买断创建合同时必须生成零售销售记录，并将设备状态设为 `sold`，不能显示为 `rented`。
- 通用编辑表单保留已有租赁设备的状态展示，但不允许选择租赁状态；后端也必须校验，不能只依赖前端禁用选项。

## 页面操作口径

- 销售管理和库存管理展示所有非完成交易设备，排除 `sold`、`peer_transfer`、`supplier_proxy`。
- `in_stock` 设备可以普通销售；预订设备可以出库，但只能走预定客户交付流程。
- 维修、租赁、外借、丢失、损坏等设备保留在列表中用于检索和台账查看，不显示销售出库操作。
- 预订设备仍可显示查看、编辑、删除按钮；删除由后端保护，必须先取消或重新处理关联预定单，避免删除后留下悬空预定。
- 划拨、调货和零售/批发销售都属于完成交易，不能再出现在销售出库和库存候选列表。

库存替代入口 `/inventory` 的列表、详情、汇总与删除均使用当前门店范围。编辑在事务锁定原记录后复用 `PhoneMutationAccessService`，只接受库存来源的明确编辑授权，同时检查原状态、原/目标门店及隐藏、只读、可编辑字段范围；不能借额外查询权限从库存入口修改完成交易设备。详情也不向库存查看权限返回完成交易设备。历史 `price` 入参仅兼容映射为 `purchase_cost`，更改成本不再自动按 1.2 倍覆盖售价；新调用使用规范字段。旧 `/phones` 后台查询入口同样检查门店并按各自模块字段脱敏，公开库存令牌接口继续沿用原有最小字段契约。

库存页面的完整编辑复用 `PUT /phones/:id?field_module=inventory_inventoryview`，查询参数只允许该精确模块键，未知值400；该来源限制为库存编辑授权，不能使用综合查询字段配置放行。先校验再锁定，并在锁内重读当前设备核验门店、状态及字段；响应只返回ID，不透传完整手机资料。三态存储及兼容规则见[库存管理三态标杆](../frontend/field-permission-guide.md#库存管理三态标杆)。

维修、租赁、外借等状态变更也应调用同一有效状态规则。它们的业务接口负责改变实体状态，展示、筛选和统计不要在页面中单独维护另一套判断。
