# 公共选项与检索统一实施方案

本文档是 TF2025 公共选项、检索接口和跨页面接入的实施规范与进度台账。后续涉及品牌、型号、颜色、内存、供应商、店铺、客户、员工、操作员或业务列表检索的修改，必须先遵循本方案，并在完成后更新本文档状态。

## 一、统一边界

### 基础选项

品牌、型号、颜色、内存、供应商属于低敏或相对稳定的基础选项，可以统一请求方式、字段、状态过滤、排序和缓存。

- 型号必须携带 `brand_id` 按品牌联动。
- 参考选项不能使用固定 `LIMIT 50/100/500` 静默截断。
- `all=true` 模式必须返回完整有效集合；关键词只缩小匹配范围，不得再次附加固定条数限制。
- 统一字段至少包括 `id`、名称字段、`status`、`sort_order`；型号增加 `brand_id`、`brand_name`。

### 权限选项

店铺可以统一请求方式，但结果必须由服务端根据当前用户的数据权限过滤。

- 综合查询必须显式使用 `strict_scope=true`，服务端只返回当前用户已绑定门店。
- 库存管理、销售管理属于库存商品查询，不启用综合查询的严格门店范围；未绑定门店的用户仍可读取商品和门店选项。
- 门店选项接口允许具备 `stores:view`、`inventory:view`、`sales:view` 或 `query:view` 任一权限的用户访问；是否严格按门店过滤由 `strict_scope` 决定。
- 严格范围请求的店铺缓存键必须包含用户或权限范围；不同用户不能共享未经权限隔离的综合查询结果。

### 敏感或大数据量选项

客户、员工、销售员、操作员不得作为全量公共选项加载。

- 统一请求参数和响应类型，但保留用途明确的查询入口。
- 必须使用关键词远程检索和分页。
- 只返回当前业务需要的最少字段。
- 必须执行用户、角色、权限和数据范围检查。

当前统一查询参数为 `keyword`、`page`、`page_size`、`status`，需要按门店筛选时增加 `store_id`。员工和操作员接口返回最少字段，并在使用分页参数或关键词时返回 `pagination.total`、`has_next` 等完整分页信息。人员查询不能依赖固定数量作为完整结果；页面应在输入关键词后远程查询。

前端人员选择器接入要求：首屏可以请求 `page_size=20` 作为候选预览，但必须同时启用 `remote`、`reserve-keyword` 和 `remote-method`，聚焦时允许使用空关键词刷新，输入关键词后继续请求 `/users/employees` 或 `/users/operators`。刷新候选时必须保留当前已选项或历史记录中的人员，避免仅因首屏分页造成回显为空。禁止把 20 条、50 条或 100 条首屏结果当作完整人员列表。

### 业务记录

库存、销售、入库、预订、维修、客户档案、员工管理等继续使用各自业务接口，不合并成一个通用列表接口。业务列表可以分页，但分页只能限制单页响应，不能截断搜索总结果；接口必须返回准确的 `pagination.total`。

## 二、实现原则

统一的重点是公共契约和公共实现，不是把所有资源合成一个大接口。

- 前端基础选项统一通过 `frontend/src/services/reference-options.ts` 公共入口调用；型号唯一入口为 `getModels({ brandId, keyword, status, includeId, activeOnly })`。未显式指定分页时默认 `all=true`，完整返回匹配集合；是否包含停用型号由调用场景显式声明，不通过多个重复包装器隐式决定。
- 后端优先保留资源路由，通过公共服务、仓储和类型规范消除重复查询逻辑。
- 业务路由继续保持独立，避免权限和字段规则互相污染。
- 返回范围、权限过滤、排序、完整性和缓存键必须与请求入口一起统一。
- 所有基础选项和存在业务排序配置的列表必须优先按 `sort_order ASC` 返回；随后按名称自然排序，最后按 `id ASC` 稳定排序。前端转换层不得丢弃 `sort_order`，必须复用 `frontend/src/utils/option-sort.ts`。
- 禁止前端使用 `slice` 或固定 `page_size` 隐藏合法选项。
- 禁止用业务列表的每页数量代替搜索结果总数。

## 三、统一接口契约

基础选项请求应使用资源明确的接口，例如：

```text
GET /brands?all=true
GET /models?brand_id=1&all=true
GET /colors?all=true
GET /memories?all=true
GET /suppliers?all=true
GET /stores?all=true
```

全量参考选项返回完整 `data` 集合；业务列表使用 `data` 加 `pagination`。如未来数据规模不适合一次返回，必须提供可继续翻页或远程关键词查询的协议，不能静默丢弃后续结果。

## 四、实施阶段

1. 审计所有基础选项、敏感选项和业务列表接口，登记请求入口、权限、排序、缓存和数量行为。
2. 统一基础选项后端响应和 `all=true` 行为，清理固定数量截断。
3. 完善店铺服务端数据权限过滤和按权限范围缓存。
4. 清理库存、销售、入库、综合查询、报价、维修等页面的重复基础选项请求，接入公共入口。
5. 为客户、员工、销售员、操作员建立关键词远程查询和用途明确的请求工具。
6. 审计业务列表的搜索字段、分页总数、下一页和导出范围。
7. 增加数量、权限、缓存隔离和跨页面一致性测试。
8. 完成文档、自动审计和回归验证后，才删除确认无调用方的旧接口或重复实现。

## 六、验收标准

- 某品牌有 200 个型号时，第 200 个型号可以检索和选择。
- 品牌、颜色、内存超过 100 条时不会静默丢失选项。
- 供应商超过 500 条时不会静默丢失选项。
- 不同用户只能看到自己有权限的店铺。
- 客户、员工、操作员不会通过公共接口全量暴露。
- 业务列表搜索超过单页数量时可以继续翻页，`total` 准确。
- 相同关键词在综合查询、库存、销售等页面的字段匹配和型号标准化规则一致。
- 文档台账、自动审计和代码实现状态一致。

兼容审计中间件为 `backend/src/middleware/compatibility-route.js`，只用于仍有调用或可能被外部调用的入口；它返回 `X-Compatibility-Endpoint`、`X-Compatibility-Id`、`X-Reference-Route`，不会伪装成已经弃用。进入删除观察期的入口使用 `deprecated-route.js`，并提供明确替代地址；动态资源路径应在替代链接中使用当前请求参数。

旧接口清理的完成条件：调用方扫描无命中、契约测试覆盖替代入口、至少一个发布周期无旧入口访问日志，再删除路由；在此之前只允许加兼容标记、统一服务和弃用记录。可运行 `cd backend && npm run audit:deprecated-routes` 按迁移 ID 汇总本地 `combined-*.log` 中的弃用访问；默认日志只保留 14 天，若发布观察期更长，必须先归档并检查完整周期的日志，不能把缺失日志当作零访问。模板及库存品牌型号选项新调用统一使用 `/brands`、`/models`、`/colors`、`/memories`，路由权限允许对应管理权限、库存查看或商城模板查看。

本轮弃用适配实现：`backend/src/middleware/deprecated-route.js`。所有进入观察期的旧入口必须复用标准处理函数，不得再复制 SQL、权限或响应转换逻辑。
