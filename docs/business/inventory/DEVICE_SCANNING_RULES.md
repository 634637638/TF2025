# 设备序列号与 IMEI 扫码规则

## 适用范围

采购入库等手机端设备录入场景统一使用 `OptimizedScanner.vue` 和 `device-scan-result.ts`，业务页面只负责指定扫码类型和接收最终结果，不得自行截取条码字符串。

## 操作顺序

1. 先选择商品品牌，再打开 IMEI 或序列号扫码。
2. 将目标条码横向对准固定蓝线，建议保持 `15-20cm` 距离和稳定光线。
3. 扫码器只会回填通过当前字段规则校验的结果；读到其他条码时显示原始内容和失败原因。
4. Apple 序列号必须先选择“苹果/Apple”品牌，解析器才能安全移除包装条码的字段标识 `S`。未选品牌时必须保留原值，防止误删其他品牌真实序列号的首字母。

## 模态框与交互

- 扫码模态框必须使用公共 `MobileDialog`，标题、关闭按钮、圆角、间距和响应式布局不得在扫码组件内重新定义。
- 底部操作区必须使用 `tf-dialog-actions`，当前命令文字为“输入”、“闪光灯/关灯”和“取消”。
- 只有取景画面、固定蓝线、识别状态和结果提示属于扫码组件的业务样式。

## 摄像头规则

- 除当前设备的 `localhost` 外，浏览器只允许在可信 HTTPS 环境调用摄像头。手机通过局域网 IP 访问时，必须使用手机已信任的 HTTPS 证书。
- 本地调试可执行 `npm --prefix frontend run cert:local -- <局域网IP>` 生成证书；手机需安装并信任 `frontend/ssl/local-ca.cer`。
- 仅创建一条摄像头流，优先使用后置摄像头；禁止业务组件提前申请流后再让解码器重复申请。
- 当页面提供固定蓝线取景框时，只解码蓝线附近的裁剪画面，不得同时对整幅画面持续解码，避免同一包装上的 SN、IMEI/MEID 和 IMEI2 互相干扰。
- 分辨率、帧率只设置 `ideal`，不得设置高分辨率 `min` 导致部分手机拒绝启动。
- IMEI 入口只按 Code128 读取手机包装上的横向条码，禁止同时启用 Code39 等可产生字母误判的码制；序列号入口可兼容 Code128、Code39、Code93、EAN、UPC、ITF、Codabar、QR、Data Matrix、PDF417 和 Aztec。解码后仍必须通过字段规则校验。
- 摄像头启动后读取真实能力，再按支持情况启用连续对焦、轻微变焦和闪光灯。
- 蓝色扫描线固定在取景框中心，禁止只做视觉动画却轮换其他解码区域。用户只需把目标条码横向对准蓝线。
- 一维码的实际解码高度应收窄在蓝线上下约 `28-38px`，不应使用整个取景框的高度；同一固定区域可同时交给 JS、WASM 和浏览器原生解码器。
- 视频使用 `object-fit: cover` 时，必须根据实际缩放比例和裁剪偏移，把屏幕取景框反向映射到摄像头原始像素；不得直接用页面 CSS 坐标当作视频像素坐标。
- 固定裁剪区域同时使用 ZXing JS 和 ZXing-C++ WASM 解码；WASM 解码必须防止多帧并发，并在停止扫码后忽略过期会话返回的结果。
- 原生解码与 WASM 应并行处理同一裁剪帧，任一通道先得到有效结果即可回填；JS 解码隔帧兜底。不得将低分辨率裁剪帧无条件放大，也不得在已限定横向对准时每帧重复尝试旋转和反色。
- Canvas 裁剪帧必须先由 `HTMLCanvasElementLuminanceSource` 将 RGBA 转为灰度亮度数据，禁止将四通道 `ImageData.data` 直接传给只接受单通道亮度数组的解码器。
- IMEI 已有 15 位长度、纯数字和 Luhn 校验，首次得到有效结果即可回填；序列号首次通过格式和类型隔离校验后也可回填，避免低清摄像头难以连续两次读取同一条码。

## IMEI 规则

- 只接收 15 位数字，并执行 Luhn 校验位验证。
- 支持纯条码、`IMEI:`、`IMEI1:`、`IMEI/MEID` 以及数字间带空格或连字符的内容。
- 二维码同时包含 `IMEI1` 和 `IMEI2` 时优先读取明确标记的 `IMEI1`。
- 苹果包装中仅识别到明确标记的 `IMEI2` 时，在通过 Luhn 校验后也可以回填；它不能与其他条码混为无标签 IMEI。
- 无标签且检测到多个有效 IMEI 时拒绝自动选择，提示用户只保留一个条码在取景框内。
- 不得通过截取复杂文本的前 15 位数字生成 IMEI，也不得因常见 TAC 前缀而跳过校验位。
- 不得向 ZXing 传入值为 `false` 的 `PURE_BARCODE` 或 `ASSUME_CODE_39_CHECK_DIGIT`；当前版本会因键存在而错误启用它们。
- IMEI 扫码入口不会接受字母序列号或商品条码，即使底层条码解码成功也会被丢弃；只有 15 位数字且 Luhn 校验通过才会回填。

## 序列号规则

- 支持 `SN`、`S/N`、`Serial No.`、`Serial Number`、`序列号` 以及 Apple `(S) Serial No.` 标签。
- 最终值统一转为大写，保留字母、数字、`/` 和 `-`，长度为 4 至 30 位；保留原始前导零。
- 序列号条码主要是 Code128、Code39、Code93、ITF 或 Codabar 横向一维码，也兼容 QR、Data Matrix、PDF417 和 Aztec，不应只按 QR 二维码处理。
- 序列号扫码入口不会接受纯数字 IMEI，即使底层条码解码成功也会被丢弃，避免 IMEI 串入序列号字段。
- 兼容部分扫码 API 返回的 AIM 条码标识（例如 `]C1`）和 GS 控制字符，这些不是设备序列号本身。
- Apple 包装的 Code128 条码会在真实序列号前加字段标识 `S`（例如条码 `SD2GVGWV67V` 对应印刷值 `D2GVGWV67V`）。只有业务已明确选择 Apple 品牌且结果为无标签单一条码时，才能移除这一位；其他品牌不得删除合法的首字母 `S`。
- 无标签的单一字母数字条码可以识别；无标签纯数字条码拒绝自动作为序列号，避免误扫商品 EAN/UPC 条码。
- 二维码包含多个字段且没有明确序列号标签时拒绝自动拼接。

## 失败兜底

摄像头权限、设备占用或浏览器能力导致启动失败时，必须提供“输入”入口。手动输入仍使用采购入库表单原有的格式校验，取消操作不得清空当前商品其他字段。

## 常见问题定位

- IMEI 显示“已读取：`CCCCCC`”：表示模糊条纹被 Code39 误判。IMEI 入口必须只启用 Code128，不得通过隐藏原始内容规避问题。
- Apple SN 多出一位 `S`：先确认是否已选择“苹果/Apple”品牌。条码 `SD2GVGWV67V` 在 Apple 上下文中应保存为 `D2GVGWV67V`；未选品牌或其他品牌保留原值是预期行为。
- 蓝线已对准但无结果：确认条码横向穿过蓝线、画面没有反光，必要时点击视频画面触发单次对焦。识别器连续约 `2.8s` 无结果时会静默重新对焦。
- 首次较慢、后续正常：WASM 需要首次加载和初始化；不得因此重复创建摄像头流或同时启动整屏解码。

## 验证要求

修改扫码功能后至少执行：

```bash
npm --prefix frontend run type-check
npm --prefix frontend run check:standards
npm --prefix frontend run build
```

真机验证应覆盖 iOS Safari、Android Chrome、标准 IMEI1、IMEI2 干扰场景、Apple 序列号（已选 Apple 品牌和未选品牌各一次）、其他品牌以 `S` 开头的 SN、错误 IMEI 校验位以及摄像头权限拒绝后的手动输入。
